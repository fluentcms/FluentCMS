# Contributing to FluentCMS v2

Thank you for your interest. v2 is early. The most useful contributions right now are review of the requirements and the architecture decision records, and work on issues in the M1 milestone.

## Where things are

| Branch | Role |
| --- | --- |
| `v2` | v2 development and the default branch. All v2 pull requests target it. |
| `dev` | v1, security fixes only. v1 pull requests must target `dev` explicitly. |
| `archive/*` | Old experiments, kept for reference, not maintained. |

- `docs/requirements/`: what v2 must do.
- `docs/adr/`: why it is built the way it is.

## Workflow: issue first

1. **Every change starts from an issue.** Pick one from the [M1 milestone](https://github.com/FluentCMS/fluentcms/milestone/2) or open one with the matching template. For anything beyond a small fix, wait for a maintainer to confirm the approach before writing code.
2. **Branch from `v2`**, named `<issue-number>-<short-slug>`, for example `2412-bootstrap-v2`.
3. **Open a pull request against `v2`.** Put `Closes #<issue-number>` in the description. Keep the pull request to its issue; unrelated changes go in their own issue.
4. **CI must pass.** Pull requests are squash-merged, so the pull request title becomes the commit title. Keep it short and imperative: "Add change set revert", not "Added revert feature".

## Authorship

Commits and pull requests are authored by the person who submits them. Do not add tool-generated co-author trailers or "generated by" footers. You are responsible for what you submit, whatever tools you used to write it.

## Labels and milestones

- `v1` or `v2`: which line the issue belongs to.
- `type:*`: `epic`, `feature`, `bug`, `chore`, `docs`, `adr`, `question`.
- `area:*`: the requirement group the work touches: `schema`, `content`, `entities`, `change-sets`, `rules`, `checks`, `routing`, `desk`, `mcp`, `audit`, `api`, `forms`, `media`, `users`, `ext`, `infra`.
- Milestones `M1 Governance core`, `M2 Built-in agent and full admin` and `M3 Scale out` follow `docs/requirements/03-feature-list.md`.

## Proposing a technical decision

Open an issue with the ADR template (label `type:adr`). Describe the context, the proposed decision, the alternatives and the consequences. If the maintainers accept it, add the record to `docs/adr/` following the format in ADR-0001, either in the pull request that implements the change or in its own pull request when the decision comes first.

## Changing a requirement

Product decisions live in `docs/requirements/00-decision-record.md`. Propose a change through an issue. The maintainers update the record; requirement documents are not edited in feature pull requests.

## Building and testing

You need the .NET 10 SDK and nothing else; `global.json` pins the version and Node is not required.

```bash
dotnet build
dotnet test
```

The admin stylesheet is compiled by the Tailwind CSS standalone CLI (ADR-0011). The first build of `FluentCMS.Admin` downloads the pinned binary (about 110 MB) once per machine into `%LocalAppData%\FluentCMS\tailwind` on Windows or `~/.cache/fluentcms/tailwind` elsewhere, verifies its SHA-256 checksum, and every build after that compiles `src/FluentCMS.Admin/Styles/app.css` into the generated stylesheet, which is not committed. For an offline build, pass the path of a binary you downloaded yourself: `dotnet build -p:TailwindExecutable=/path/to/tailwindcss`. CI restores the cache directory keyed on the pinned version. The version and checksums live in `src/FluentCMS.Admin/Tailwind.targets`.

Tests run against SQLite in-process. To run the PostgreSQL tests as well, set `FLUENTCMS_TEST_POSTGRES` to a connection string for an empty database, for example `Host=localhost;Port=5432;Database=fluentcms_test;Username=postgres;Password=postgres`. CI does this with a service container. Without the variable those tests are skipped.

The browser tests drive the admin in headless Chromium through Playwright: keyboard-only review on the desk and automated WCAG 2.1 AA checks with axe-core. They run when `FLUENTCMS_TEST_BROWSER` is set. Install the browser once after a build with `pwsh tests/FluentCMS.IntegrationTests/bin/Debug/net10.0/playwright.ps1 install chromium`; CI installs it and sets the variable.

To run the host, `dotnet run --project src/FluentCMS.Host` starts the web host on `http://localhost:5000` with a SQLite database in `fluentcms.db`, and `dotnet run --project src/FluentCMS.Host -- mcp` starts the stdio mode. Configuration comes from environment variables such as `Database__ConnectionString`, `Database__Provider` (`sqlite` or `postgresql`, inferred from the connection string when omitted), `JobQueue__WorkerCount`, `Content__DeletedRetention` (how long a deleted entry or media asset can be restored, `30.00:00:00` by default), `Entities__VerifyWithin` (how long a fact stays verified before it is listed as stale, `180.00:00:00` by default), `Delivery__PreviewTokenLifetime` (how long a preview token works unless it is revoked or its change set ends, `7.00:00:00` by default), `Media__Storage` (the storage new uploads go to, `local` by default), `Media__LocalDisk__Root` (where the local storage keeps bytes, `media` under the content root by default) and `Media__MaxBytes` (the largest upload, 50 MB by default; over MCP on HTTP, the server's 30 MB request limit holds an upload to about 22 MB, since base64 grows a file by a third), and from an optional `appsettings.json` next to the binary.

Agents reach the MCP server (ADR-0007) through either mode. The web host serves streamable HTTP at `/mcp` in stateless mode: each request stands alone, no session id is issued, and a GET answers 405 because the server never opens a stream to the client. `fluentcms mcp` serves the same server over standard input and output to an agent that starts it as a local process, for example with `dotnet run --project src/FluentCMS.Host -- mcp` as its command. It reads the same settings as the web host, so pass it the web host's `Database__ConnectionString` and `DataProtection__KeysDirectory` to work on the same database and key ring. Relative paths resolve against the process's working directory, so give an agent absolute ones. Standard output carries only protocol messages, log lines go to standard error, and the process stops when its standard input closes. The stdio mode runs with the local user's database access, so it is meant for development and single-user setups. Clients on protocol revision 2026-07-28 connect with `server/discover`, earlier ones with `initialize`. Agents read content types, the schema document and change sets with the read-only tools, and propose changes with `open_change_set`, `create_content_type`, `revise_content_type` and `submit_change_set`. A write stores an unpublished version and its operation in the agent's change set together, and the version is not published until a person approves and publishes the set; no tool approves, rejects or publishes. Agents follow review with the read-only desk tools: `get_desk_counts`, `list_desk_queue` and `get_change_set_review`, which see only the change sets the agent opened.

Every MCP call runs as an agent and needs that agent's key, issued on `/agents/new`. Over HTTP the key goes in the `Authorization: Bearer <key>` header of each request; `/mcp` reads no other credential, so a signed-in person's admin cookie is ignored there. Over stdio the key goes in the `FLUENTCMS_AGENT_KEY` environment variable of the process, which an agent's MCP configuration can set; it is never read from a command-line argument, which other users can see in process listings. Both transports check the key on every request or message, so an expired or revoked key is refused from its next call on, with a message that says why. Never put a key in a URL: the server ignores one there, but ASP.NET Core logs request URLs once `Logging__LogLevel__Microsoft.AspNetCore` is below its shipped `Warning`. Every tool call is recorded in the `ToolCalls` table with the agent, the tool, the outcome and how long it took. An agent can add the model it runs on and the task it works on as strings in the call's `_meta`, under `fluentcms/model` and `fluentcms/task`, and the record keeps both. Arguments and results are not recorded; the audit log records every change a tool makes.

Core checks every call against the agent's scope and caps, so a tool and a form cannot disagree:

- Reading a content type or its entries needs `read` on the type, and lists leave out types the agent may not read.
- Writing an entry needs `create`, `update` or `delete` on its type, plus `read`. Every field the write changes must be allowed by the field list; a field sent back unchanged is not a change.
- A type's definition covers every field, so creating, revising or proposing one needs a scope that does not narrow that type to some of its fields.
- A call past the credential's calls per period does not run. It returns an error result that names the cap, and refused calls do not count toward it. A call is recorded as `running` before its tool runs and counts from then, so concurrent calls of one agent take turns at the cap, as its change set opens do at the daily cap.
- An agent reads, adds to, submits and reopens only the change sets it opened. People read every set.

On a fresh database the admin asks for the first administrator at `/setup`; every other admin page needs a signed-in user. Data Protection keeps the keys that protect sign-in cookies, anti-forgery tokens and stored secrets in `DataProtection__KeysDirectory` (default `data-protection-keys` under the content root). Put it on storage that survives restarts and upgrades and that only the host's account can read; losing it signs everyone out. Sign-in, setup and password reset posts are limited per client address by `SignInRateLimit__PermitLimit` and `SignInRateLimit__Window`, ten a minute by default. A password reset link issued on `/users` works once and expires after `PasswordReset__TokenLifespan`, one day by default. Each agent connects with its own key, issued on `/agents/new` with a scope, caps and an expiry. The key is shown once, in the response that issues it, and only its SHA-256 hash is stored. A lost key cannot be recovered: issue a new one and revoke the old one on `/agents`.

Signed in, `/ui` shows every component in `src/FluentCMS.Admin/Components/Ui` with its keyboard hints. Switch the theme from the header and the direction with the link on the page. A new component goes on that page in the same pull request; a test fails when one is missing.

A shadcn example translates into Razor with the same class names. `ClassNames.Cn` is shadcn's `cn()`: it joins the classes and merges them as tailwind-merge does, so a later class replaces an earlier one that sets the same property and a component's `Class` parameter overrides its own classes. `Variants` is shadcn's `cva()`, with the base classes, the classes for each value of each variant, and the defaults; `ButtonVariants` and `Badge` use it.

Icons are Lucide's, one component each in `src/FluentCMS.Admin/Components/Icons`, named as in lucide-react (`XIcon`, `ChevronDownIcon`), hidden from assistive technology and sized by the classes around them. To add one, put its Lucide name in `src/FluentCMS.Admin/Icons/icons.txt`, run `dotnet build src/FluentCMS.Admin -t:GenerateIcons` and commit the generated component; a normal build does not download or generate anything. `Icons.targets` pins the Lucide release and the SHA-256 of its archive and of its licence. Lucide is ISC licensed, and the icons it took from Feather are MIT; both notices are in `Icons/LICENSE`.

`src/FluentCMS.Admin/wwwroot/js/admin.js` is the admin's only JavaScript, and no component calls into it: it listens on the document and reads the page when an event arrives, so behaviour keeps working while the circuit is down and after a reconnect. A keyboard shortcut is declared on the element it triggers with `aria-keyshortcuts`, for example `aria-keyshortcuts="Control+K Meta+K"`, which assistive technology announces as well. The module clicks a button or link and focuses anything else. A shortcut without Control, Alt or Meta waits while someone types in a field, and while a modal dialog is open only the shortcuts inside it apply.

People can also sign in through one OpenID Connect provider (Keycloak, Authentik, Microsoft Entra, Google and similar). Set `Authentication__OpenIdConnect__Authority`, `Authentication__OpenIdConnect__ClientId` and `Authentication__OpenIdConnect__ClientSecret`, optionally `Authentication__OpenIdConnect__DisplayName` for the button, and register `https://<host>/signin-oidc` as the redirect URI at the provider. Without an authority and client id the option does not appear. Users are not created from the provider: the first sign-in links the provider's account to the user with the same email, and only if the provider marks the email as verified. Later sign-ins match on the provider's issuer and subject. A provider that never sends `email_verified`, such as Microsoft Entra, needs `Authentication__OpenIdConnect__AssumeVerifiedEmail=true`; set it only if that provider issues verified addresses alone.

## Database migrations

Each provider has its own `DbContext` subclass and migrations folder (ADR-0005). After changing the model, add a migration for both; no database needs to be running, the design-time factories build the model on their own.

```bash
dotnet tool restore
dotnet ef migrations add <Name> --project src/FluentCMS.Infrastructure --context SqliteFluentCmsDbContext --output-dir Persistence/Migrations/Sqlite
dotnet ef migrations add <Name> --project src/FluentCMS.Infrastructure --context PostgreSqlFluentCmsDbContext --output-dir Persistence/Migrations/PostgreSql
```

Migrations apply automatically when the host starts. Every migration needs a working `Down`, since upgrades must be reversible one version back (OPS-04).

## Units of work and the audit log

Every operation that changes data runs inside a unit of work and appends the audit event that describes it from inside the same scope, so the two commit together or not at all (AUD-N1, ADR-0005). `IUnitOfWork.BeginAsync()` returns a scope; `CommitAsync()` saves and commits, and disposing a scope without committing rolls everything back, including saves that Identity makes on its own inside it. Inner scopes join the outer transaction, and an inner scope disposed without committing makes the outer commit fail. `IAuditLog.AppendAsync(new NewAuditEvent("entry.updated") { ... })` stamps the current initiator and time itself, and throws outside a unit of work or when no initiator is known, so a change without provenance cannot exist. The initiator is a person, an agent, or a `SystemInitiator` naming a part of the product that acts on its own (ADR-0012): the check engine (`checks`) moving a set out of checks running, or a retention purge (`retention`). A system initiator never opens a change set, reads but never writes content, and makes only the moves `AgentPermissions` lists for its component.

Nothing in the code updates or deletes an audit row. On PostgreSQL the `AuditEvents` migration also revokes `UPDATE`, `DELETE` and `TRUNCATE` from `PUBLIC` and from the role that applies it, which owns the table. A superuser bypasses privilege checks, so run the host, which applies migrations at startup, as an ordinary role that owns the database. SQLite has no roles; there the code is the guarantee.

`IAuditReader.Read(AuditQuery)` reads the log back: an optional window from `From` (inclusive) to `To` (exclusive) and an optional `AuditSubject` for one item's history, oldest first with ties broken by id, streamed from the database. With no window and no subject it is the full log. An inverted window or an incomplete subject is a failed `Result`. `IAuditExporter.ExportAsync` writes the same selection to a stream as JSON or CSV while it reads it, after committing an `audit.exported` event that names who exported and, for one item's history, the item; viewing history is a read and records nothing. Both formats carry the same fields under the same names, in this order: `id`, `timestamp`, `operation`, `initiatorKind` (`user`, `agent` or `system`), `initiatorId`, `initiatorName`, `agentCredentialId`, `subjectType`, `subjectId`, `model`, `promptHash`, `sources`, `changeSetId` and `previousVersionId`. The JSON is an array of objects with every key present and `null` for an empty field. The CSV follows RFC 4180 with a header row and CRLF line ends, plus three conventions so every value reads back exactly: `sources` is one cell holding a JSON array, an unquoted empty cell is null while a quoted one is an empty string, and a value starting with `=`, `+`, `-`, `@`, a tab, a carriage return or `'` gets one leading `'`, so a spreadsheet does not run it as a formula; a reader drops that one `'`.

The admin's `/audit` page offers the export and an item's history. A page cannot answer with a file, so its export form posts to `POST /audit/export` in the host, which maps the form, calls the exporter and streams the result; it needs a signed-in user and an anti-forgery token like every form, and sends a rejected form back to the page.

## Background jobs

Work that outlives a request, such as a bulk operation or a check run, is a job in the `Jobs` table (ADR-0010). Enqueue it with `IJobQueue.EnqueueAsync(new NewJob(type, payload) { Subject = ..., RunAt = ..., MaxAttempts = ... })` inside the unit of work of the change that needs it, so the job commits with the change or not at all; outside a unit of work it throws, as the audit log does. The job records the current initiator, and its handler runs as them, so what it changes names whoever asked for it. A handler for work no person or agent does, such as the check run a submission starts, names a `SystemInitiator` in `RunAs`, and its jobs run as that engine whoever enqueued them, while the job still records who did (ADR-0012). `IJobQueue.GetAsync` and `ListForSubjectAsync` read a job's state (`queued`, `running`, `succeeded`, `failed` or `dead`), attempts, progress and last error.

A handler implements `IJobHandler` (an extension point) with the type name its jobs store, which never changes once released. It reads the payload from `JobContext.Job`, resolves services from `JobContext.Services`, a scope of its own, and reports progress with `ReportProgressAsync`, which also keeps its lease; when that returns false another worker has the job, and the handler stops. A returned failure ends the job as `failed`. An exception retries it after `JobQueue__RetryDelay`, doubled for each attempt up to `JobQueue__MaxRetryDelay`, and after its last attempt the job is `dead`. Work in a handler therefore has to be safe to run again.

`JobQueue__WorkerCount` workers in the host claim due jobs every `JobQueue__PollingInterval`. A claim holds a job for `JobQueue__LeaseDuration`, which the worker renews at a third of it while the handler runs. A renewal that fails is tried again while the lease holds, and no wait or renewal lasts past the lease's end. The handler's cancellation token fires as soon as the lease is lost or its end passes with no renewal, because another worker may then claim the job; a handler should honour it. A job whose worker stopped is claimed again once the lease runs out, counting another attempt. A host that stops while a handler runs puts the job back in the queue with its attempt given back. Claims are conditional updates on the row, so with any number of workers, in one host or several, each job runs once at a time.

## Model access

Every model call goes through `IModelGateway` in `FluentCMS.Core.Models` (ADR-0008). Nothing else holds a model client: only `FluentCMS.Infrastructure` references a provider package, and a test fails when other code uses one.

- **Profiles.** A caller names a profile, such as `checks`, and an administrator points it at a provider: `Models__Profiles__checks__Provider` (`openai` for any OpenAI-compatible endpoint, including LiteLLM, OpenRouter, Ollama, LM Studio and vLLM, or `anthropic`), `__Model`, `__Endpoint` (the provider's own when left out), `__ApiKey`, `__InputCostPerMillionTokens` and `__OutputCostPerMillionTokens` in US dollars, `__MaxOutputTokens` and `__Timeout`. An endpoint is https, or http to a server on the same machine. An endpoint off this machine needs both prices, since a call without them costs nothing and no spend cap refuses it, unless `__Free` says it charges nothing. Put keys in the environment or a secret store, never in a committed file. An Anthropic profile needs its own key, so the SDK never uses credentials it finds on the machine. A profile the host cannot use stops it at startup with what to change.
- **No model.** With no profile configured, `IsAvailable` is false and a call fails with `model_not_configured`. The governance loop still runs, and a caller degrades, for example to needs review (MDL-03).
- **Prompts.** A request carries the caller's own instructions apart from untrusted data, and the gateway builds the structured prompt. Content, rule text and sources go only in `ModelData` sections, never into the instructions (SEC-03).
- **Allow-list.** Outbound requests go only to hosts in `Outbound__AllowedHosts`. An entry allows its subdomains too, and an entry with a port, such as `localhost:11434`, allows that port only. A profile whose endpoint is not allowed is refused, and the provider HTTP clients refuse any other host and do not follow redirects (SEC-05).
- **Spend.** A call is charged to the calling agent (SEC-04), and a person's calls are not capped. An engine asks a model only for a person's or an agent's work and names them in `OnBehalfOf`, so an agent's call counts against its cap; only an engine names someone else, and an engine call that names no one, or a call with no initiator, is refused. Before it is sent, it is recorded as pending at the most it can cost, one token per byte of prompt plus the profile's output limit. It goes out only if that fits under what is left of the agent's `LlmSpendPerPeriod` for its `LlmSpendPeriod`. An answered call then costs what the provider counted, and a failed one, or an answer without token counts, keeps its reserved cost, since it may have been charged. The SDKs do not retry, so each attempt is a call on record.
- **Records.** Every call is kept in `ModelCalls` with its provider, model and version, verbatim prompt and response, tokens, cost and outcome (MDL-04, CHK-05). Audit events carry its prompt hash, and `IModelCallLog.FindByPromptHashAsync` finds the prompt again. A provider's error stays in the record; the caller gets the record's id. A call is made outside a unit of work, so the database is not held while a provider answers, and making one inside one throws.
- **Retention.** Prompts and responses are kept for `Models__PromptRetention`, 90 days by default, which must be longer than every profile's timeout. A call purged while it waits for its answer stays purged. A person runs `IModelCallLog.PurgeAsync`, which clears the prompt, response and error of older calls, keeps the rest of each record, and appends a `model_call.purged` event for each call (AUD-04, AUD-N2).

## Webhooks

An administrator adds a webhook on `/webhooks` with the URL of an endpoint and the events it is told about, `change_set.published` and `change_set.reverted` (API-05). Only a person lists, adds or disables one; an agent is refused (SEC-02).

- **URL.** It is https, or http to an endpoint on the same machine, and its host is on `Outbound__AllowedHosts`, the allow-list the model gateway uses. Nothing can be added until an administrator names a host (SEC-05). A URL with a user name or password in it is refused. A URL is never edited: disable the webhook and add a new one.
- **Secret.** Each webhook gets a signing secret, 32 random bytes written as `whsec_` and base64, shown once in the response that adds it. It is stored encrypted with the Data Protection key ring, so losing `DataProtection__KeysDirectory` loses the secrets too. It never appears in a list, a log or the audit log (SEC-07).
- **Audit.** Adding and disabling append `webhook.added` and `webhook.disabled`, which name the subscription.

Deliveries, their signature and how a receiver checks it come with the next slice.

## Extension points

Every pluggable part of the product is an interface in `FluentCMS.Core` marked `[ExtensionPoint]`. Implementations register through dependency injection, either explicitly with `AddFluentCmsExtension<TContract, TImplementation>()` or by discovery with `AddFluentCmsExtensions(assembly)`, which picks up every concrete class implementing an extension-point interface in that assembly. Both paths produce the same `IExtensionCatalog` entry and the same `IEnumerable<TContract>` resolution, so built-ins under `FluentCMS.Core.Builtin` and future plugins look identical to the rest of the product. Each interface is documented where it is defined, together with the conformance tests an implementation must pass.

Field types (`IFieldType` in `FluentCMS.Core.Schema`) are the first. A field type has a name that definitions store, so it never changes once released, and it checks the settings a definition gives a field of its type, returning errors for missing, invalid and unknown settings instead of throwing. `FieldSettingsReader` does that bookkeeping for built-ins and plugins alike. A type whose values point at entries of another content type, or at one field of an entity type such as `product.price`, also implements `ReferenceTargets`; `IContentTypeDirectory` refuses a definition whose targets do not exist in the site, or whose field targets are not fields of an entity type, so a plugin type gets the same checks as the built-in `reference`. Such a type also lists the references each stored value makes (`References`), with a JSON Pointer to each one's place; entries write them to the reference index that where used (`IWhereUsed`, CNT-05) reads, and refuse a reference to an entry that is missing or of another type. Every type also describes its values for the schema document agents read (`DescribeValue`, SCH-06): a JSON Schema for one value, an example that satisfies it and one sentence about it. It checks each value an entry stores in a field of its type (`ValidateValue`), accepting what it describes and returning `value_invalid` errors for anything else; `IEntryDirectory` stores no version with a value its type refuses. To add one, implement the interface, then derive a test class from `FieldTypeConformanceTests` in `tests/FluentCMS.Tests/Schema` with settings the type must accept and settings it must reject, and values it must accept and reject; a type outside Core also overrides `AddFieldTypes` to register its assembly.

Media storage (`IMediaStorage` in `FluentCMS.Core.Media`, MED-04) holds the bytes of media assets. A storage has a name that every asset stores, so it never changes once released; it saves a stream and hands back an opaque key with the length and SHA-256, opens a key for reading and deletes one, and treats a key it did not hand out as not found, never as a path. The local disk storage, `local`, ships in Infrastructure. To add one, implement the interface, register it with `AddFluentCmsExtension<IMediaStorage, T>()` and derive a test class from `MediaStorageConformanceTests` in `tests/FluentCMS.IntegrationTests/Media`; `Media__Storage` then names it, and the host refuses to start with a name nothing registered.

Agent tools and resources (`IToolProvider` and `IResourceProvider` in `FluentCMS.Core.Tools`, MCP-02, MCP-03) are next. A tool has a snake_case name, which agents and the tool call log know it by, so it never changes once released. Its description, and the description of every argument in its input schema, are written for the model that reads them: what the tool does, when to call it and what to call next. Build the schema with `ToolSchemas`, which describes each argument with an example and refuses arguments it does not name. Read the arguments with `ToolArgumentsReader`, which reports a missing, malformed or unknown argument by name before the tool reads anything. Return a `ToolResult`: the value as JSON, or the errors of a `Result`, each with a code and a message that says what to change, plus an optional hint naming the call that finds a valid value. The MCP server sends a failure as a tool error (`isError`) with `{"errors", "hint"}` in both the structured content and the text, never as a protocol error, so the agent reads it and tries again. A resource has a fixed URI or a template such as `fluentcms://schema/{slug}`. To add a provider, implement the interface, then derive a test class from `ToolProviderConformanceTests` in `tests/FluentCMS.Tests/Tools`. Two tools with one name stop the host when it starts. A new tool also adds its row to `McpCoverageTests`, the MCP-01 list of capabilities and the tools that cover them, which fails for a tool no row names.

Check types (`ICheckType` in `FluentCMS.Core.Checks`, CHK-06) follow. A check type has a name that checks store, so it never changes once released, and a kind: deterministic, or LLM-judged for a type that asks a model. It checks the settings a check gives it as a field type does, with `CheckSettingsReader`, and evaluates one subject to an outcome: pass, fail with findings, or needs review when it cannot decide. The subject holds the fields of a piece of content, narrowed to the fields the check's scope names, the sources its change cites, and its content type and definition when it has one. A finding says what to change (UX-03), points at the place with a JSON Pointer into the fields (empty for the content as a whole) and can quote the text it found. A type returns an outcome whatever the content holds and never throws; a type that is not installed, or that throws anyway, evaluates to needs review, never to a pass. The input also carries the caller's services, for a type that needs more than the content. To add one, implement the interface, then derive a test class from `CheckTypeConformanceTests` in `tests/FluentCMS.Tests/Checks` with settings the type must accept and reject and content it must pass and fail; a type outside Core also overrides `AddServices` to register its assembly.

An LLM-judged type asks a model only through `IModelGateway`, which it reads from the input's services, with the `checks` profile. Its instructions are written in code. The content and its own settings go in `ModelData` sections, since an author or a rule wrote them (SEC-03, RUL-07). With no model it returns needs review without a call (MDL-03), and an answer it cannot read is needs review as well. It passes the input's `OnBehalfOf` to its request, so a call an engine makes for a change set counts for whoever opened it; without it, an engine's call is refused and the check needs review. It attaches the call to its outcome with `WithModel`, so the result names the model call that keeps the prompt and response (CHK-05). The built-in `tone`, `readingLevel` and `claims` types work this way. The built-in `instructions` check flags text that reads as instructions to a model in property names as well as values, and reads text as a model may: compatibility forms decomposed, accents dropped and look-alike letters of other scripts mapped to Latin, so `ｉgnore` or a Cyrillic `іgnore` hides nothing.

A check is a versioned definition under a slug: a check type and its settings, a description of what it enforces, a severity (block or warn), an optional scope of content types and fields, and test examples, at least one it must pass and one it must fail. `ICheckDirectory` activates a version only after running its examples, and names each example that does not get its verdict (CHK-02). A revision leaves the active version in place until the new one is activated, and only a person activates or deactivates a check. `ICheckRunner` runs the active checks that apply to a piece of content and gives each one's status: pass, warn for a failing check of warn severity, fail, or needs review. Agents run it on a draft with the `check_draft` tool before they propose it (CHK-04).

A submitted change set is checked as the check engine (`SystemInitiator.Checks`, ADR-0012), never as the agent: submit it through `IChangeSetChecks.SubmitAsync`, not by moving it to checks running yourself. While every active check is deterministic, a set of up to 50 operations is checked on the request that submits it; any other set is checked by a `checks.run` job, which reports its progress (PERF-02). Every entry and entity the set creates or updates is checked at the version it proposes, and an LLM-judged check asks the model on behalf of whoever opened the set, so an agent's call counts against its cap (SEC-04). An item the engine cannot read, such as an entry deleted since, is a problem that fails the run. So is a job whose last attempt throws, and a set whose job ended without moving it is failed when it is submitted again, so it can be reopened. A reopened set is fixed in place: a set holds one operation per item, and a later draft of an entry or entity it already proposes, the same change from the same published version, moves that operation on to the new draft and appends `change_set.operation_updated`. Each run names its submission's job, and a run of an earlier submission changes nothing. A revert is never held by its checks: it goes to review with their results (CHG-06). The run, each item's results with their findings and model calls, and the move it decides (checks failed when a check fails, otherwise awaiting review) commit together, numbered per set, with the audit events `change_set.checked` and `check.judged` (CHK-03, CHK-05). Agents read the run of the latest submission and its job with the `get_change_set_checks` tool, which shows a job's state and progress but not the error a worker recorded.

Search (`ISearchIndex` in `FluentCMS.Core.Search`, SRC-01, ADR-0010) indexes each entry's latest version in the same unit of work as the write, as the lowercase words of every string and number in its fields (`SearchText`), so a result appears the moment its write commits. PostgreSQL keeps them in a `tsvector` with a GIN index and SQLite in an FTS5 table, both outside the EF model and created by their migrations; an external engine implements the same interface, registered with `AddFluentCmsExtension<ISearchIndex, T>(ServiceLifetime.Scoped)` when it needs the request's scope. `ISearch` combines the matches with the entry rows, so deleting, restoring and publishing change results without touching the index, follows a match to the entries that reference it, and returns only types the caller may read. It reads the matches a page at a time, `Search__PageSize` (1,000 by default), and drops what the scope, deletions and filters leave out, until enough are left, the index has no more, or it has read `Search__MaxMatches` (10,000). A result that stopped there says it is not complete. Each hit has the state the entry tools show, in review included. A string that is a GUID, such as a reference, is not indexed. Field filters (`SearchQuery.Fields`) compare one type's latest field values, an entity's by its fact's value, and `SearchQuery.References` keeps entries whose latest version references an id; both are checked against the type before anything is read and applied to each page's candidates. With one type and either filter the text can be left out, and the candidates are then that type's entries.

## Code style

`.editorconfig` is the source of truth: UTF-8, LF line endings, four spaces in C#, two in JSON and YAML, file-scoped namespaces. Nullable reference types and implicit usings are enabled project-wide. Prefer clear code over clever code. Comments explain why, not what. Do not add XML documentation comments unless an issue asks for them.
