# System migrations

`SystemDbContext` is the model of the system tables: what `SystemModelBuilder` maps, with no content tables and with the history table `cms__migrations`. Each data provider package holds the migrations of that model for its database, in its `Migrations` folder.

## The baseline

The first migration of each provider's set is the baseline, `Initial`, scaffolded from the model of the first preview ([#3052](https://github.com/fluentcms/FluentCMS/issues/3052)). It replaced the twenty migrations (twenty-one on SQL Server) that the build had made up to then, none of which was published, and so does `Initial` in each plugin's stream ([plugin migrations](plugin-migrations.md)).

Previews make no promise to upgrade a database until 1.0.0: a later preview may need a new one. A database made by the migrations from before the baseline is refused at start and by `fluentcms migrate`, before anything is applied, with `FCMS1307`, and `fluentcms doctor` names it among the reasons the host would not start. The check reads the history of the system stream and of each plugin stream, and refuses one that holds migrations but not the stream's first:

```text
FCMS1307: stream system has applied 20261102151133_InitialSystem but not its baseline 20261113071031_Initial; nothing was applied: the database was made by the migrations from before the baseline, which a preview does not upgrade, so recreate it (on SQLite, delete its file) and apply the migrations again
```

The baseline carries what the model cannot say and the scaffold therefore does not write: on SQL Server its first step turns `READ_COMMITTED_SNAPSHOT` on, outside a transaction ([ADR 0005](decisions/0005-sql-server-read-committed-snapshot.md)), so that a user without `ALTER` on the database stops it before anything is created. Because that step runs outside the transaction of the others, EF logs `NonTransactionalMigrationOperationWarning` once when it applies `Initial` on SQL Server; the warning is expected. It leaves out what the chain left only because it upgraded databases that had rows: the default of `cms_role.require_two_factor`, a column it added to a table with rows, and the raised stamp of the Author role, whose seeded grants it changed. EF writes every column on insert, and a new database caches no grant. `BaselineTests` in `tests/FluentCMS.Data.Tests/Migrations` compares a database built by the baseline with one built by the SQL of the old chain, which the test project keeps as test data in `Migrations/BeforeBaseline`, on the provider of the run.

## Adding a migration

Do this in the pull request that changes `SystemModelBuilder`, such as one that adds `cms_site` or `cms_job`. You need the `dotnet-ef` tool (`dotnet tool install --global dotnet-ef`). No database is needed, because the design-time factory in each package never connects.

1. Map the table in `SystemModelBuilder`.

2. Scaffold the migration once per provider, with the same name. `dotnet ef` starts a fresh context each time, which matters: scaffolding on a context that has already called `HasPendingModelChanges()` silently emits `CreateTable` for every table.

   ```bash
   dotnet ef migrations add AddSites --project src/FluentCMS.Data.Sqlite --context SystemDbContext --output-dir Migrations
   ```

   ```bash
   dotnet ef migrations add AddSites --project src/FluentCMS.Data.PostgreSql --context SystemDbContext --output-dir Migrations
   ```

   ```bash
   dotnet ef migrations add AddSites --project src/FluentCMS.Data.SqlServer --context SystemDbContext --output-dir Migrations
   ```

3. Add `// <auto-generated />` as the first line of each new migration file. EF marks only the designer and snapshot files, and the composite index columns in the migration file otherwise fail the build with CA1861.

4. Run `dotnet test --project tests/FluentCMS.Data.Tests -c Release`. The tests fail if a provider's snapshot no longer matches the model, so a skipped provider is caught.

A migration that changes the grants of a seeded role also raises `permissions_version` of that role, with `migrationBuilder.Sql` and relative to its current value, because the seed cannot say what a live role has reached and the evaluator's cache is keyed on the stamp. Add the statement to the scaffolded `Up` and `Down`.

Do not edit a migration that has shipped. Every data test database on PostgreSQL and SQL Server is built by these migrations, so CI applies them on PostgreSQL 15 and SQL Server 2019 and 2025 ([#2711](https://github.com/fluentcms/FluentCMS/issues/2711)).

## Applying them

A host applies the system stream first, then the plugins' streams and its content stream: at start when `FluentCms:Database:MigrateOnStartup` is true (the default on SQLite), or with `fluentcms migrate`, which an upgrade to a new FluentCMS version needs on PostgreSQL and SQL Server, where startup otherwise stops with `FCMS1305`. `fluentcms migrations script --stream system --idempotent` writes the SQL of these migrations for a database that only an administrator may change ([content migrations](content-migrations.md#applying-migrations)).
