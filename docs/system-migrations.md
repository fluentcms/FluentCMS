# System migrations

`SystemDbContext` is the model of the system tables: what `SystemModelBuilder` maps, with no content tables and with the history table `cms__migrations`. Each data provider package holds the migrations of that model for its database, in its `Migrations` folder.

## Adding a migration

Do this in the pull request that changes `SystemModelBuilder`, such as one that adds `cms_site` or `cms_job`. You need the `dotnet-ef` tool (`dotnet tool install --global dotnet-ef`). No database is needed, because the design-time factory in each package never connects.

1. Map the table in `SystemModelBuilder`.

2. Scaffold the migration once per provider, with the same name. `dotnet ef` starts a fresh context each time, which matters: scaffolding on a context that has already called `HasPendingModelChanges()` silently emits `CreateTable` for every table.

   ```bash
   dotnet ef migrations add AddSites --project src/FluentCMS.Data.Sqlite --context SystemDbContext --output-dir Migrations
   ```

   ```bash
   dotnet ef migrations add AddSites --project src/FluentCMS.Data.PostgreSql --context SystemDbContext --output-dir Migrations
   ```

   ```bash
   dotnet ef migrations add AddSites --project src/FluentCMS.Data.SqlServer --context SystemDbContext --output-dir Migrations
   ```

3. Add `// <auto-generated />` as the first line of each new migration file. EF marks only the designer and snapshot files, and the composite index columns in the migration file otherwise fail the build with CA1861.

4. Run `dotnet test --project tests/FluentCMS.Data.Tests -c Release`. The tests fail if a provider's snapshot no longer matches the model, so a skipped provider is caught.

A migration that changes the grants of a seeded role also raises `permissions_version` of that role, with `migrationBuilder.Sql` and relative to its current value, because the seed cannot say what a live role has reached and the evaluator's cache is keyed on the stamp. Add the statement to the scaffolded `Up` and `Down`.

Do not edit a migration that has shipped. Every data test database on PostgreSQL and SQL Server is built by these migrations, so CI applies them on PostgreSQL 15 and SQL Server 2019 and 2025 ([#2711](https://github.com/fluentcms/FluentCMS/issues/2711)).
