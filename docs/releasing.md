# Releasing

`FluentCMS.Sdk` is the public contract that plugins and host code compile against, and it follows semantic versioning: breaking changes ship only in a major version, and every removal is announced with `[Obsolete]` at least one minor version earlier. The build enforces this with two checks, described below.

## How the build enforces the contract

- **Public API analyzer.** `Microsoft.CodeAnalysis.PublicApiAnalyzers` compares the public surface of `FluentCMS.Sdk` with `PublicAPI.Shipped.txt` and `PublicAPI.Unshipped.txt` in `src/FluentCMS.Sdk`. A public member that is in neither file fails the build with `RS0016`; a listed member that no longer exists fails with `RS0017`.
- **Package validation.** `EnablePackageValidation` compares the packed assembly with the last released package and fails `dotnet pack` on a removed or changed member (`CP0001`, `CP0002` and related codes).
- **XML docs.** Every public member needs an XML doc comment, because a missing one is `CS1591` and warnings are errors.

During development, add new public members to `PublicAPI.Unshipped.txt`. The `RS0016` code fix in the IDE does this for you. A removal or signature change is recorded in `PublicAPI.Unshipped.txt` as a `*REMOVED*` line followed by the new entry, and is allowed only while preparing a major version.

## One version

Every package, the image and `@fluentcms/client` carry one version. `Directory.Build.props` holds its prefix, `VersionPrefix` (1.0.0, decision 61), and a release takes the whole version from its tag: the tag `v1.0.0-preview.1` packs every package as `1.0.0-preview.1`. Any other build is a pre-release that no release has: `1.0.0-ci.{run id}.{attempt}` on GitHub Actions, `1.0.0-dev` elsewhere, and `1.0.0-fresh.{time}` from a local run of `eng/fresh-machine.ps1`, so a package of CI can never be taken for a release. `FluentCMS.Templates` names its own version in the projects it makes, the image is built with `--build-arg VERSION`, and the Pack job sets the version of `@fluentcms/client` with `npm version`.

A version with a pre-release part, such as `1.0.0-preview.1`, is a preview. Until 1.0.0 the contract may break between previews (spec 10.4, H1): every entry stays in `PublicAPI.Unshipped.txt` and no package validation baseline is set. A tag must name a version of the prefix in `Directory.Build.props`, so raise the prefix in a pull request before the tag of a new version, and after a release that is not a preview, so that the builds of CI come after it.

## Package metadata

Every package has a description, a README (the `README.md` beside its project, which `Directory.Build.props` packs), its tags, with `fluentcms-plugin` on every package of `src/plugins` (decision 15), the icon, the licence expression `MIT`, the repository with its commit, and SourceLink in the PDB of its assembly: in the `.snupkg` beside it, or embedded in the assembly for the analyzers and the generator. The `Pack` job of CI runs [`eng/check-packages.cs`](../eng/check-packages.cs) on the packages it packs, which names each part a package misses and fails the job, and then checks that a copy of `FluentCMS.Sdk` without each of those parts, SourceLink included, fails it. SourceLink is expected to point at the origin of the clone that packed, which is a fork's own repository on a fork. `@fluentcms/client` has a description, the licence and a README.

## The Publish workflow

[`.github/workflows/publish.yml`](../.github/workflows/publish.yml) publishes a release. A tag `v*` starts it, and its jobs are:

1. **Check the release.** It refuses a tag that is not `v` and a version, a version that is not of the prefix in `Directory.Build.props`, a pre-release `ci`, `dev` or `fresh`, a tag without its notes in `docs/releases/{version}.md`, a tag that has a GitHub release already, a commit that is not on `main`, a commit with no successful run of `CI` or no successful `Fresh machine` job on Linux and on Windows that tested its own packages (from CI, or from the `Fresh machine` workflow on a push or a manual run without a feed; a run with a feed has names of its own and does not count), and a `release` environment that does not exist, has no required reviewer or deploys to anything but the tags `v*`. The environment is read through the API with the job's `GITHUB_TOKEN`, which the environments of a public repository allow; the environment and the list of its deployment policies need the same access, so when either cannot be read the check refuses and names the endpoint. A refused tag publishes nothing, and no job names the environment, so GitHub never makes one without a reviewer.
2. **Pack.** Every package of the solution at the version of the tag, `@fluentcms/client` at the same version, and the metadata check.
3. **Image.** The image of the reference host for `linux/amd64` and `linux/arm64`, tagged with the version and with `preview` for a preview or `latest` for a release that is not one.
4. **What a release pushes.** The list of the packages, the client and where it goes, the image and its tags, and the GitHub release, in the log and the summary of the run.
5. **Publish**, in the `release` environment, after its reviewer approves, and only when the environment holds `NUGET_USER`: the image to `ghcr.io/fluentcms/fluentcms` first, since a package on nuget.org can be unlisted but never deleted, then every package with its symbols to nuget.org, signed in with trusted publishing, and `@fluentcms/client` to npm with the dist-tag `next` for a preview (`latest` otherwise) when the repository variable `NPM_SCOPE_OWNED` is `true`.
6. **GitHub release.** The release of the tag with its notes, a pre-release for a preview, with the `.tgz` of `@fluentcms/client` attached while it is not on npm.

**Run workflow** on **Actions → Publish**, with or without a tag to rehearse, is a dry run: it runs the first four jobs, reports each refusal of the commit as a warning instead of stopping, and pushes nothing. A pull request that changes this workflow, `Directory.Build.props`, a project file under `src/`, the templates' project, the Dockerfile or the client's `package.json` runs the same dry run, with no environment and no secret, and skips the checks of the commit. Only the publish job holds a credential, and none is a repository secret that a pull request can read: nuget.org gives a key of one hour for the policy of this workflow and environment, the image is pushed with the job's `GITHUB_TOKEN`, and npm uses trusted publishing too once it has a policy.

## The maintainer's part

No workflow can do these; each is done once, before the first release, by an owner of the organization on GitHub and of the `FluentCMS` organization on nuget.org:

- **nuget.org prefix.** Reserve the ID prefix `FluentCMS.` for the `FluentCMS` organization (decision 61), and unlist and deprecate, with a pointer to the replacement, the existing IDs that have no successor. New packages that reuse an existing ID start at 1.0.0.
- **nuget.org trusted publishing.** Under **Trusted Publishing** of the account, add a policy owned by the `FluentCMS` organization with the repository owner `fluentcms`, the repository `FluentCMS`, the workflow file `publish.yml` and the environment `release`. A policy that nuget.org shows as temporarily active needs a publish within seven days, and can be restarted.
- **The `release` environment.** In **Settings → Environments**, create `release` with **Required reviewers** (the maintainers who approve a release), and under **Deployment branches and tags** allow the tags `v*` only. Add the environment secret `NUGET_USER`, the nuget.org user name (the profile name, not the email address) of the account that made the policy. With npm, add the environment secret `NPM_TOKEN`, a granular token that may publish `@fluentcms/client`, for the first publish only: npm configures trusted publishing per package, once the package exists, with the organization `fluentcms`, the repository `FluentCMS`, the workflow `publish.yml` and the environment `release`; remove the token then. Make the environment before the first tag, and rehearse with a manual run of `Publish` on `main`, whose check reads it and warns of what is missing.
- **npm.** Once the `@fluentcms` scope on npm is the project's, set the repository variable `NPM_SCOPE_OWNED` to `true` in **Settings → Secrets and variables → Actions → Variables**. Until then the client is attached to the GitHub release.
- **The tags.** A tag ruleset on `v*` (**Settings → Rules → Rulesets**, a new tag ruleset, active, targeting `v*`, with **Restrict creations**, **Restrict updates** and **Restrict deletions**, and only the maintainers in its bypass list). It is required: a tag runs the `publish.yml` of the commit it names, so anyone else with write access could tag a commit off `main` whose workflow skips the checks.
- **The image.** The first publish creates the private package `fluentcms` of the organization. In its **Package settings**, change the visibility to public, and check under **Manage Actions access** that the repository `FluentCMS` has the role write, which the next publishes need. If the organization does not allow public packages, allow them first in **Organization settings → Packages**.

## Cutting a release

1. Check that the commit to release on `main` has a successful `CI` run, which includes the `Fresh machine` jobs on pushes to `main`, or run them with **Actions → Fresh machine → Run workflow**. They run [`eng/fresh-machine.ps1`](../eng/fresh-machine.ps1), which packs every package into a folder feed and, on a clean runner, installs the templates and the `fluentcms` tool from it, makes a Blog host with `dotnet new fluentcms`, runs `migrations add` and `migrate` on SQLite (and on PostgreSQL on Linux), makes an administrator and a key, compiles the output of `generate typescript`, exports the site and imports it into a second new host, and builds and tests a plugin from `dotnet new fluentcms-plugin`. The Linux job then checks that a package that misses a file and a template that names a wrong version fail the script. The script runs on a developer's machine too (PowerShell 7.4, the .NET SDK and Node.js); beyond the repository's own build output, it leaves nothing behind but its work directory.
2. For a release that is not a preview: in `src/FluentCMS.Sdk`, move every entry from `PublicAPI.Unshipped.txt` to `PublicAPI.Shipped.txt`. Keep the `#nullable enable` first line in both files, keep `PublicAPI.Shipped.txt` sorted, and leave `PublicAPI.Unshipped.txt` with only the `#nullable enable` line. For a `*REMOVED*` line, delete the entry it names from `PublicAPI.Shipped.txt` and drop the `*REMOVED*` line itself. Commit the two files with the release, for example `Ship public API for 1.1.0`. A preview skips this step.
3. Write the notes in `docs/releases/{version}.md`, such as `docs/releases/1.0.0-preview.1.md`, in a pull request into `main`, and wait for `CI` on the commit it makes.
4. Rehearse with **Actions → Publish → Run workflow** on `main` and the tag, such as `v1.0.0-preview.1`. The run lists every package, the image and its tags, and warns of what a release would refuse.
5. Tag the commit and push the tag: `git tag -a v1.0.0-preview.1 -m "FluentCMS 1.0.0-preview.1"` and `git push origin v1.0.0-preview.1`. Check the list of the run, and that its commit, which the run's page and the summary of **Check the release** name, is in the history of `main` on GitHub, since the workflow that ran is the tagged commit's own; then approve the `release` environment under **Review deployments**.
6. After the first publish, make the image public (above). Then run the new user's path against what was published: **Actions → Fresh machine → Run workflow** with the feed `https://api.nuget.org/v3/index.json` and the version, a run named `Fresh machine of the published {version}` whose jobs are `Published packages (…)`, once nuget.org lists the packages (indexing takes some minutes), which takes `@fluentcms/client` from the GitHub release while it is not on npm; and **Actions → Compose → Run workflow** with the image, such as `ghcr.io/fluentcms/fluentcms:1.0.0-preview.1`. Locally, `pwsh eng/fresh-machine.ps1 -Feed https://api.nuget.org/v3/index.json -Version 1.0.0-preview.1 -Client <the .tgz of the release>` does the same.
7. For a release that is not a preview, open a follow-up pull request that sets `PackageValidationBaselineVersion` in `src/FluentCMS.Sdk/FluentCMS.Sdk.csproj` to the version that was just released, so the next release is compared with it, and raises `VersionPrefix`. Until 1.0.0 has shipped there is no baseline and the property is absent; the first release adds it.

A run that fails after the approval is rerun with **Re-run failed jobs**: the image tags are pushed again, and nuget.org skips the packages it holds already. A version that reached nuget.org is never published again; the next preview takes the next number. A tag that the check refused is deleted and made again on the right commit.

## Breaking changes

- A breaking change to a shipped member lands only in a major version.
- Announce the removal one minor version ahead: mark the member `[Obsolete("Use X instead.")]` in a minor release, then remove it in the next major. The compiler warns a plugin author who uses an obsolete member (`CS0618`). A `FluentCMS.Analyzers` rule for obsolete SDK members follows with the first member that is marked `[Obsolete]`; until then the package holds the schema rules only ([analyzer rules](analyzers.md)).
- For a major version, set `PackageValidationBaselineVersion` to the last release of the previous major, and record each intentional break by running `dotnet pack -c Release -p:ApiCompatGenerateSuppressionFile=true`. Review the generated `CompatibilitySuppressions.xml` in the pull request, and delete it once the major has shipped and the baseline has moved to it.
