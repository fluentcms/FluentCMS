## Additions

- `fluentcms schema apply` lists under `Left alone:` a content text column whose collation is not the model's, `C` on PostgreSQL and `Latin1_General_100_BIN2` on SQL Server, and `--script` writes the line as a comment: `column title on table cms_article, whose collation is the database's default and not C as in the content model; schema apply does not change a collation, so a sort and a cursor on the column follow the one it has until it is altered by hand`. Such a column is one of a table made before #3308 on PostgreSQL or before #2874 on SQL Server, or one altered by hand. Schema apply does not change it, with `--allow-destructive` neither, since the change rebuilds the column's indexes and locks the table, SQL Server refuses it on an indexed column, and it moves what every sort and cursor on the column returns. On PostgreSQL alter the columns with the statements that the query in the notes of #3308 writes. On SQL Server drop the indexes and statistics on the column, alter it with its own type and nullability, as `ALTER TABLE cms_article ALTER COLUMN title nvarchar(max) COLLATE Latin1_General_100_BIN2 NULL`, and run `fluentcms schema apply`, which makes the indexes again. A PostgreSQL database whose own collation is `C` lists its columns too, until they are altered to `COLLATE "C"`. SQLite's model gives no collation, so nothing is listed there (#3476).
- The specification states the order of text on each provider. SQLite and PostgreSQL sort content text by code point. SQL Server sorts it by UTF-16 unit, which differs only around U+FFFF: a character at U+10000 or above, such as an emoji, comes before one in U+E000 to U+FFFF there, such as `Ａ` (U+FF21) or U+FFFD, and after it on SQLite and PostgreSQL. A cursor continues each provider's own order correctly. A client that sorts or compares pages itself compares by UTF-16 unit for SQL Server, as JavaScript's `<` does, and by code point for SQLite and PostgreSQL. Content moved to another provider can list such texts in another order (#3476).
