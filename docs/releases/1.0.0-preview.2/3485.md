## Changes that break code built before this preview

- An export holds the database snapshot it reads its entries from for at most `FluentCms:Transfer:ExportSnapshotTimeout` (1 hour, at most 1 day, a new option), counted from the start of the snapshot, not from when a reader stalls: an export whose entries take longer to go out, however steadily its package is read, is stopped. The client sees the connection reset after the 200, with nothing that names the option: `fluentcms export --url` fails with `FCMS3252` and writes no file, as it now also does when the handler reports the reset as a plain `IOException` of the transport, which it printed as it was; `fluentcms export` run in the host fails with a cancellation that names the option. The server logs warning 9190, which names the option, and writes no `transfer.exported` activity row. Raise the option for such exports, as `FluentCms__Transfer__ExportSnapshotTimeout=02:00:00`. Where the database gives no snapshot, as on a default SQL Server database, the bound does not apply (#3485).
- An export that stops before its package is whole, at the bound or for any other reason, writes nothing more, the central directory of the zip included, so its bytes are never a smaller package that opens: the import refuses them with `FCMS3200`. Such an export completed the zip with the files written so far (#3485).

## Fixes

- A request with an `Idempotency-Key` whose work answered before its client went away keeps that answer although the client went away while it was being written, so a retry with the key is answered it, with `Idempotent-Replayed: true`, and runs nothing. The key was held without an answer until its lease ran out, and a retry then ran the request again. A client that goes away while the work still runs leaves the key held without an answer, as before, so a bulk cut short, which answers 200 with its remaining items not run, keeps nothing, and a retry after the lease runs it again. That window stays open: a create whose commit is done but whose client went away before the service returned, as while the entry is read back, where a client's timeout most often lands, and a bulk whose first items committed, still run again on a retry after the lease. Writing an answer after the client left takes `InProgressTimeout` at most; one that takes longer is not kept, logged with the new event 9147, and the key can then be held for up to twice `InProgressTimeout` (#3485).
