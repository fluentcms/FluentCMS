## Changes that break code built before this preview

- A save of a plugin's `PluginDbContext<T>` that adds a row with a `site_id` column, or moves a row to another site, holds the row of that site in `cms_site` until it commits, as a content write that adds an entry does, so a site's deletion waits for it and its row goes with the site's cleanup. A save for a site that is gone is refused with `FCMS2301` (`ValidationException`), also on an instance whose cache still has the site; it was saved and stayed as a row of a site that no longer exists. This covers the rows of the media, webhooks, MCP, multi-site, search and AI assist plugins, and a third-party plugin's; a save outside a transaction now runs in one of its own. A media upload or import refused so deletes the file it wrote (#3485).
- The default `IDataProvider.LockSiteAsync` reads `cms_site` by its name for a context whose model has no `Site`, such as a plugin's (#3485).
- An export holds the database snapshot it reads its entries from for at most `FluentCms:Transfer:ExportSnapshotTimeout` (1 hour, at most 1 day, a new option). An export whose package is read more slowly is stopped, its response is aborted without the end of the zip, so no reader takes it for a whole package, `fluentcms export` writes no file, and warning 9190 is logged. Where the database gives no snapshot, as on a default SQL Server database, the bound does not apply (#3485).

## Fixes

- A request with an `Idempotency-Key` whose client goes away after its write committed, as while its answer is written, keeps that answer, so a retry with the key is answered it, with `Idempotent-Replayed: true`, and runs nothing. The key was held without an answer until its lease ran out, and a retry then ran the write a second time. Once the client has gone, the answer is written for `InProgressTimeout` at most; one that takes longer is not kept, logged with the new event 9147, and the key is held until its lease ends, as before (#3485).
