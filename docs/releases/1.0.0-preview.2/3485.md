## Changes that break code built before this preview

- An export holds the database snapshot it reads its entries from for at most `FluentCms:Transfer:ExportSnapshotTimeout` (1 hour, at most 1 day, a new option), counted from the start of the snapshot, not from when a reader stalls: an export whose entries take longer to go out, however steadily its package is read, is stopped. The client sees the connection reset after the 200, `fluentcms export` fails with a cancellation that names the option and writes no file, warning 9190 is logged, and no `transfer.exported` activity row is written. Raise the option for such exports, as `FluentCms__Transfer__ExportSnapshotTimeout=02:00:00`. Where the database gives no snapshot, as on a default SQL Server database, the bound does not apply (#3485).
- An export that stops before its package is whole, at the bound or for any other reason, writes nothing more, the central directory of the zip included, so its bytes are never a smaller package that opens: the import refuses them with `FCMS3200`. Such an export completed the zip with the files written so far (#3485).

## Fixes

- A request with an `Idempotency-Key` whose work answered before its client went away keeps that answer although the client went away while it was being written, so a retry with the key is answered it, with `Idempotent-Replayed: true`, and runs nothing. The key was held without an answer until its lease ran out, and a retry then ran the request again. A client that goes away while the work still runs leaves the key held without an answer, as before, so a bulk cut short, which answers 200 with its remaining items not run, keeps nothing, and a retry after the lease runs it again. Writing an answer after the client left takes `InProgressTimeout` at most; one that takes longer is not kept, logged with the new event 9147, and the key can then be held for up to twice `InProgressTimeout` (#3485).
