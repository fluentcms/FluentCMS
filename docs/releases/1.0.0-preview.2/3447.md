## Changes that break code built before this preview

- The wrong current passwords and the wrong two-factor codes of a signed-in user's sessions are counted apart, each with the limit and time of `FluentCms:Users:Lockout`, as the user tokens `SignedInFailures` and the new `SignedInCodeFailures`. A right code starts only the count of codes again: it left a session that holds the second factor free to give four wrong passwords on `/account/change-password`, one right code at `/me/two-factor/recovery-codes`, and start again. It also no longer starts the lockout's count of failed sign-ins again, which a right password still does. Either count at its limit still keeps the user's sessions out of both, and a `SignedInFailures` stored before this preview counts as wrong passwords (#3447).
- A password change checks the new password against the policy before the current one, so a new password the policy refuses gets the policy's answer whatever the current password given, counts nothing, and is not counted towards the lockout. It answered a wrong current password, counted, first, and the policy only for a right one, which told the sender the guess was right (#3447).
- `CmsUserManager.SignedInAccessFailedAsync` and `CmsUserManager.ResetSignedInFailuresAsync` are removed: core counts and starts each count again itself, by kind (#3447).
- `IDataProvider.IsUniqueViolation(Exception, IUniqueConstraint)` is a new member, with a default of `false`, that tells one key of the model from the others: PostgreSQL by the constraint its error names; SQL Server by the key's name in single or double quotes in the message of 2601 or 2627, looked for only before the message's first parenthesis, since the duplicate value ends the message in parentheses; and SQLite by the key's columns, which end its message. The part of a message that repeats the duplicate value is never read. A message of SQL Server in another language is read the same way, as long as it quotes the name in one of those two quotes; one that quotes it otherwise has a save of a user that meets another's on the key of `cms_user_token` thrown instead of refused, as has a provider other than the three of FluentCMS. Core found that key by the name of the table anywhere in the message, which SQL Server's duplicate value could hold too (#3447).

## Fixes

- Wrong current passwords or codes a session sends at once are checked no more than the lockout's limit, however many they are. They all read the user before any of them saved, so only one was counted, and a right password among them was checked without being counted and answered either way: a concurrency failure when its save lost, which told the sender it was right. A guess now takes its place in its count, in a save that goes through and is made again on what is stored when it loses, before it is checked. One that finds the sessions kept out is refused unchecked, and one whose tries at a place run out, twice the lockout's limit, ends with the concurrency failure, unchecked too. A wrong one keeps its place and counts towards the lockout; a right password takes the new one in a save that gives its place back, made again when it loses, and is answered as a wrong one if its tries run out; a right code is taken in the save of its step, and one that loses it is refused like a wrong one, since a code is taken once (#3447).
- A call of `CmsUserManager` whose save fails puts back the flag of the forced password change, or the deactivation, only when that save did not reload the user with what is stored, which another request may have changed. Put back over a reload, the stale value would have been stored by a later save in the same scope, which could have reactivated a user another request deactivated; no caller of core saves again after such a failure, so this was latent (#3447).
- `docs/host-configuration.md` no longer says that the token endpoint refuses a code or refresh token of a user who is locked out, which #3271 ended (#3447).
