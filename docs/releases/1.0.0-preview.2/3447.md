## Changes that break code built before this preview

- The wrong current passwords and the wrong two-factor codes of a signed-in user's sessions are counted apart, each with the limit and time of `FluentCms:Users:Lockout`, as the user tokens `SignedInFailures` and the new `SignedInCodeFailures`. A right code starts only the count of codes again: it left a session that holds the second factor free to give four wrong passwords on `/account/change-password`, one right code at `/me/two-factor/recovery-codes`, and start again. It also no longer starts the lockout's count of failed sign-ins again, which a right password still does. Either count at its limit still keeps the user's sessions out of both, and a `SignedInFailures` stored before this preview counts as wrong passwords (#3447).
- `CmsUserManager.SignedInAccessFailedAsync` and `CmsUserManager.ResetSignedInFailuresAsync` are removed: core counts and starts each count again itself, by kind (#3447).
- `IDataProvider.IsUniqueViolation(Exception, IUniqueConstraint)` is a new member, with a default of `false`, that tells one key of the model from the others: PostgreSQL by the constraint its error names, SQL Server by the first two names its message quotes for 2601 and 2627, which come before the duplicate value, and SQLite by the key's columns, which end its message. A provider other than the three of FluentCMS has a save of a user that meets another's on the key of `cms_user_token` thrown instead of refused. Core found that key by the name of the table anywhere in the message, which SQL Server's duplicate value could hold too (#3447).

## Fixes

- Wrong current passwords a session sends at once on `/account/change-password` are each counted, and those past the limit refused. They all read the user before any of them saved, so only one was counted, and a right one among them that lost its save answered with a concurrency failure, which told the sender it was right. A password change, or a code at `/me/two-factor`, whose save loses to another save of the user is now made again on what is stored, so a wrong one is counted before it is answered as wrong and a right password is taken; a right code that loses the save that takes it is refused like a wrong one, since a code is taken once. Only when its saves keep losing, twice the lockout's limit in a row, is a guess answered with the concurrency failure, whether it was right or wrong (#3447).
- A call of `CmsUserManager` whose save fails puts back the flag of the forced password change, or the deactivation, only when that save did not reload the user with what is stored, which another request may have changed. A later save in the same scope stored the stale value (#3447).
- `docs/host-configuration.md` no longer says that the token endpoint refuses a code or refresh token of a user who is locked out, which #3271 ended (#3447).
