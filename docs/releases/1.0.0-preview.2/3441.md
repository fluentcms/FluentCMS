## Changes that break code built before this preview

- `IMcpClients.ListConsentsAsync` and `IMcpClients.EndConsentAsync` are new members with no default, which an implementation other than core's must add (#3441).
- The record `McpClientInfo` of the MCP plugin, the answer of `/mcp/clients`, has two more positional parameters, `UsedAt` and `UsedBy`, after `LastActivityAt`, so code that constructs or deconstructs it changes with it (#3441).
- A consent that would keep one MCP client more than `maxConsentsPerUser` ends on the hosted error page with `consent_limit_reached`, whose sentence tells the user to end a consent they no longer use or to ask an administrator. It ended there with `invalid_request` (#3441).
- This corrects the note of #3397 on what counts toward `maxConsentsPerUser`: a client the `open` policy approved counts for a user while the user holds a consent to it, one ended by its session or a password change included until the prune of the authorization server removes it, and for the user who first consented to it for as long as it is there, until that user ends the consent with `DELETE /api/management/v1/mcp/consents/{id}`. It does not count without limit for every user who consented to it once (#3441).

## Additions

- `GET /api/management/v1/mcp/consents` lists the MCP clients the `open` policy approved that count toward the caller's `maxConsentsPerUser`, each with `id`, `clientId`, `name`, `redirectUris`, `registeredAt`, `consentedAt` and `active`, a consent ended by its session or a password change included, and `DELETE /api/management/v1/mcp/consents/{id}` ends the caller's consent to one of them and frees its place. It deletes the caller's authorizations of the client with their tokens, so its access tokens stop at once, and the client no longer names the caller as `usedBy`; one that then holds no grant of anyone goes as a client never used, after `neverUsedClientHours`. Both need no permission and are the caller's own: a client that counts for another user, or for none, is `FCMS1603`, answered before any lock is taken, and a caller that is no user has none. An end that crosses another change, a token issued under the consent meanwhile included, is `FCMS1609` and ends nothing, and the same call again ends it. The end of a valid consent is the activity row `user.sessions_ended` with the reason `revoked` (#3441).
- The consents that take a place, the end of one and the cleanup's write of a client's first user run one at a time under the database lock `fluentcms:mcp-consents`, each counting what the others committed, so consents given at the same moment never pass `maxConsentsPerUser`, and a user whose consent ends while the cleanup writes `usedBy` is not named again. They passed it by as many as were in flight (#3441).
- When that lock is not free within 45 seconds, the consent page ends on the hosted error page with `temporarily_unavailable` and records nothing, and `DELETE /mcp/consents/{id}` answers 503 with `FCMS3106` and ends nothing (#3441).
- `GET /api/management/v1/mcp/clients` answers `usedAt` and `usedBy` of each client, the time and the user of its first consent, and so do `McpClient.UsedAt` and `McpClient.UsedBy` (#3441).
- Event 9008 names the list of the user and the end of a consent: `Refused the consent of the user {UserId} to the MCP client {ClientId}: the user keeps {MaxConsentsPerUser} clients that the open policy approved already, as GET /api/management/v1/mcp/consents lists them to the user, some of them perhaps with a consent that was ended. The user frees one with DELETE /api/management/v1/mcp/consents/{id}; an administrator removes the clients not in use, or raises MaxConsentsPerUser.` (#3441).
