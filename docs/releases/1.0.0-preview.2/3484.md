## Changes that break code built before this preview

- An SVG uploaded, replaced or imported from a package file with `Svg` set to `sanitize` loses every `<style>` element, whatever it holds, since a page that inlines the SVG would apply its rules to the whole page; `style` attributes stay, except on the root `<svg>`. A drawing whose colours were in a `<style>`, as many editors export them, loses them (#3484).
- Every `id` of such an SVG, and every reference to one in `href`, `xlink:href`, `url(#…)`, `aria-labelledby`, `aria-describedby` and the `begin` and `end` of an animation, takes the prefix `fcms_`, sixteen hex digits of the SHA-256 of the sanitised file as written before the prefix, and an underscore, so that an inlined SVG puts no name on `window`, clashes with no id of the page or of another SVG and reaches no element of the page. The underscores keep `begin="fcms_…_a.end"` an id and an event, where a hyphen would be read as an offset. A reference to no id of the file takes it too. A prefix of that form that the file carries already is kept only when taking it off and scoping the file again gives the same bytes, as for a file the plugin sanitised before; otherwise every name takes the file's own on top. A page or script that found an element of the SVG by its id finds it under the new one (#3484).
- The root `<svg>` of such an SVG loses its `overflow`, `style`, `transform` and `filter`, and an animation of the root that sets one of them or the root's `width`, `height`, `x`, `y`, `viewBox` or `preserveAspectRatio`, or an `animateTransform` or `animateMotion` of the root, goes; an animation whose `href` or `xlink:href` names the root counts as one of the root. A `style` or other value read as CSS that holds `element(` or `-moz-element(` goes, as does an animation whose `attributeName` is `class` or `id`, and a `begin` or `end` list with a value the timing grammar does not read whole, such as one with a backslash, a no-break space or a parenthesis in an id, or with `accessKey(…)` or `wallclock(…)`; an animation whose `begin` went starts when the drawing loads (#3484).
- A `class` name on an inlined drawing picks up whatever the page's CSS gives that class, which with utility CSS includes position; the page's box for the drawing is what holds it (#3484).
- These remove the ways out of its box that are known; they do not promise there is no other. What keeps an inlined drawing inside its place is the page's own box for it, with `overflow: hidden` and `contain: paint` (#3484).
- An SVG that nests elements more than 128 levels deep, the root included, or holds more than 100,000 nodes (elements, text, CDATA sections, comments and processing instructions), or has an element with more than 1,000 attributes, namespace declarations included, is refused as a file that is no SVG (`FCMS1581`), whatever `Svg` says. Those limits bound the time sanitising takes: each pass sets an element's children and attributes again once, where a file of about 1 MB of many removed elements took tens of seconds before (#3484).
- Stored SVGs are not changed. An import line without a file that names the key of an SVG stored by an earlier build is refused with `FCMS3220`, since sanitising it now gives other bytes; a file of the package is sanitised and taken. Serve SVGs stored before this change through the CMS, which sends them with its `Content-Security-Policy`, and do not inline them in a page or serve them through a CDN that drops that header (#3484).

## Fixes

- An SVG uploaded with `Svg` set to `sanitize` could run script in a page that inlines it: a CDATA section in a text element, under a root with a namespace prefix such as `<s:svg>`, was stored as it was, and a page that parses the file as HTML reads such a section as a comment that ends at its first `>`, so what follows became markup of the page, an `<img onerror=…>` for one. A sanitised SVG is now written with SVG as the default namespace and no prefix on any element, with no XML declaration, CDATA section, comment or processing instruction, and with text and values escaped, so that an HTML parser reads it as an XML parser does. The hole existed before this preview. SVGs already stored are not changed: serve them through the CMS with its sandbox, and do not inline them (#3484).
- A sanitised SVG is written with `\n` for a new line on every platform, so that sanitising it again on another one gives the same bytes and an import line can take its key (#3484).
