## Changes that break code built before this preview

- A request with an `Idempotency-Key` whose `FluentCms:Idempotency:Window` ends while it still runs keeps its key: a repeat answers 409 (`FCMS3142`) until it answers, and the retention job leaves the key, instead of claiming or removing it and letting the repeat run beside the request, which was then cancelled with `FCMS3142` and event 9145 as if the repeat had taken its key over. Once the request has answered, the expired key is claimed afresh and a repeat runs again, as before, which the 409's message now says (#3523).
- Another request with such an expired `Idempotency-Key`, whose first request still holds its lease, answers 409 (`FCMS3142`); it claimed the key afresh and ran (#3523).
- A request whose `Idempotency-Key` a repeat took over after its write committed, as while the entry was read back, answers what it wrote (201 with the entry, or the bulk result). It answered 409 (`FCMS3142`) with a message that said its write was rolled back. Its answer is not kept, since the key is the repeat's (#3523).
- A repeat that takes over a key whose lease ran out loses to a renewal of that lease that comes between its read and its update, and answers 409 (`FCMS3142`); both requests ran until the first one's next renewal (#3523).

## Additions

- A request whose key passed its window and was removed after its lease ran out puts its claim back at its next renewal and goes on holding the key, logged with the new event 9146, so its response is kept for a repeat; if another request claimed the key first, the request is cancelled as after a takeover (#3523).
