## Changes that break code built before this preview

- A grant with a row rule gives content permissions alone. A grant of `*`, `users.manage`, `roles.manage`, a `settings.{area}.manage` or a plugin's permission with a `rowRule` held that permission in full and now holds it nowhere, and gives a plugin's `ResourcesOf` no resource; the content a `*` with a rule reaches stays under the rule. A user, a key or a member who held such a permission only through such a grant loses it, which can take `roles.manage` or `users.manage` from an administrator; Super Admin, whose `*` has no constraints, keeps everything. The role of an MCP client that registered itself limits every call through the client, so a client role whose `*` or other permission outside content has a row rule now leaves calls through that client no core, settings or plugin permission, whatever the user's own roles hold. To find the grants, read `GET /api/management/v1/roles` as a Super Admin, which lists the roles of every site, and look for a grant with `constraints.rowRule` whose `permission` does not start with `content.`. Give the permission without the rule to keep what it gave, or `content.*.*` with the rule for what `*` with it meant (#3443).
- `POST /roles`, `PUT /roles/{id}` and the import of roles refuse a row rule with 422 `FCMS3042` on `grants[n].constraints.rowRule` beside a permission that is not of content alone (`*`, `*.*.update`, a core, settings or plugin permission), and on a content type the rule is not registered for, which for a pattern of every type, such as `content.*.update`, is any content type of the schema; such a role was saved, and the rule then matched no row of that type. A role stored with such a grant is still read and exported, and an import of a role identical to the stored one is skipped, but an edit, or an import that would change the role, is refused until the grant or its rule is dropped. An import validates a role before it checks `roles.manage`, as it does for an unknown rule, so a caller with `transfer.manage` alone sees the refusal and the types it names in the report, in a dry run too (#3443).
- A grant of every type with a rule registered type by type, such as `content.*.read` with a rule of its own for each type, stops fitting when a content type is added to the schema and the rule is not registered for it: the grant gives no row of the new type, and every `PUT /roles/{id}` of its role, a rename or a change of `requireTwoFactor` too, is refused with `FCMS3042` naming the new type. Register the rule for the new type as well, or drop the grant, or replace it with one grant per type the rule has (#3443).
