## Changes that break code built before this preview

- On SQL Server and PostgreSQL a start with `MigrateOnStartup` and a `fluentcms migrate` take the migrations lock before they check the database against the baselines, so one that arrives during another process's migration waits and then goes on, where it failed at the command timeout. One with nothing pending waits too, for up to 15 minutes. On SQL Server this takes the lock on every such start and needs a connection pool that allows two connections (#3528).
- A wait for the lock that times out before the checks ends in `so this run migrated no stream`, where the error named the first stream as not migrated (#3528).
- The runner calls `IDataProvider.LockMigrationsAsync` before its checks, and `TakeMigrationsLockAsync` on the system stream's context around them and on each stream's before it reads what is pending, so also for a stream with nothing to apply. A provider of your own that implements either must not keep the lock on a pooled connection when the call or the disposal fails (#3528).

## Additions

- A release of the migrations lock that fails is logged as a warning with event 9307 and no longer replaces the outcome of the migration. The providers of SQL Server and PostgreSQL release every share, with a timeout of 5 seconds, or close the connection, so that no lock stays in the pool after a failed or cancelled migration (#3528).
- A database that another process is creating is no longer refused with `FCMS1308` as one of an earlier baseline, by a start, `migrate` or `doctor` (#3528).
- `docs/content-migrations.md` gives the query that finds the session holding the lock on each server, and lists the waits that the command timeout still ends (#3528).
