## Changes that break code built before this preview

- An upload, a new media folder or preset, a line of the media import that adds a folder or an asset, a new webhook, new MCP guidelines, instructions or stored prompt, a new host name of a site and a search write that adds entries of a site now hold the row of their site in `cms_site` until they commit, as a content write that adds an entry does, so a deletion of the site waits for them and their rows go with the site's cleanup. One for a site that is gone is refused with `FCMS2301` (422, `ValidationException`), also on an instance whose cache still has the site; it was saved and stayed as a row of a site that no longer exists. An upload or an import line refused so deletes the file it wrote, and an import reports the line with `FCMS2301`; a search delivery refused so is tried again by the outbox. Each such write runs in a transaction of its own: up to one begin, one statement and one commit more. AI usage rows and webhook deliveries hold nothing and are left to their retention jobs, which remove the rows of a site that is gone with the others (#3586).
- The default `IDataProvider.LockSiteAsync` reads `cms_site` by its name for a context whose model has no `Site`, such as a plugin's, and a third-party data provider whose own `LockSiteAsync` reads `context.Set<Site>()` must do the same (#3586).

## Additions

- `PluginDbContext<TPlugin>.HoldSiteAsync(SiteId site, CancellationToken cancellationToken = default)` holds the row of a site shared to the end of the context's current transaction, for a plugin's own writes of a site's rows, and is refused with `FCMS2301` when the site is gone. Without an open transaction of the context it throws `InvalidOperationException`; it begins none of its own. A plain save holds nothing, as before. Hold several sites in ascending order of `SiteId.Value`, and never in a content hook, where on SQL Server a deletion of the same site queued meanwhile and the hold wait for each other until a timeout fails the content write (#3586).
