## Changes that break code built before this preview

- On SQL Server a start with `MigrateOnStartup` or a `fluentcms migrate` that waits for another process's migrations no longer fails at the command timeout with `Execution Timeout Expired`. It logs event 9305 once after 30 seconds and fails after 15 minutes with a `TimeoutException` that names EF's application lock `__EFMigrationsLock` and says that another process is applying migrations; `migrate` exits with 1 and `FCMS3302`, as on SQLite (#3192).
- On PostgreSQL the same wait, for the advisory lock of the whole run, which had no end and logged nothing, logs event 9305 once after 30 seconds and fails after 15 minutes in the same way, naming the migrations lock of FluentCMS (#3192). A migration that runs longer than 15 minutes now makes the processes that wait for it fail; apply it from one `fluentcms migrate` before the hosts start.
- Event 9305 names the lock in the property `Lock`, which replaces `Written`; on SQLite it holds the row of `__EFMigrationsLock` and its time, and the message reads as before (#3192).

## Additions

- `IDataProvider.TakeMigrationsLockAsync` takes EF's migrations lock before EF does, on the connection of the stream's context, for a provider whose lock EF waits for no longer than a command may run; its default takes nothing, so a provider other than core's builds and behaves as before (#3192).
