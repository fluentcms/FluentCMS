The second preview of FluentCMS, a headless CMS for .NET, and the first with its admin. Every package is on nuget.org as `1.0.0-preview.2`, the twelve of the admin among them, and the image of the reference host is `ghcr.io/fluentcms/fluentcms:1.0.0-preview.2`, for `linux/amd64` and `linux/arm64`; the prebuilt static build of the admin, `fluentcms-admin-1.0.0-preview.2.zip`, is on the GitHub release; `@fluentcms/client` for TypeScript is on npm as `@fluentcms/client@1.0.0-preview.2` under the dist-tag `next`. The contract can still break between previews, and a preview makes no promise to upgrade a database.

These notes name the changes since `1.0.0-preview.1`: the admin first, then the limits that still hold, what breaks code or a database built before this preview, what was added and what was fixed.

## The admin

The first preview of the admin of FluentCMS, the Blazor WebAssembly app in which editors manage content and media, and administrators users, roles, keys, members, sites, settings, plugins and jobs. It is a client of the Management API alone, and signs the users of the instance in on its hosted login page. `docs/admin.md` is the overview. It comes in three distributions, the same app built from the same packages:

- **At `/admin` of the API host**, for most setups: the image serves it, and so does a host made with `dotnet new fluentcms`, which adds `FluentCMS.Admin.Hosting` with the prebuilt build it carries unless `--admin false` is given. Open `{public origin}/admin/`, such as `https://localhost:5443/admin/` for a template host in Development, and sign in as an administrator of the instance. The sign-in needs https.
- **The prebuilt static build**, for the first-party admin on a static host or a CDN: `fluentcms-admin-{version}.zip` on the GitHub release, with the recipes of `docs/admin-hosting.md`, and on the API host the two settings of an admin on another origin (`docs/admin-configuration.md`).
- **An app of your own**, for a team with admin halves of its own plugins: `dotnet new fluentcms-admin`, with the administration pages, the rich text editor and the six first-party halves as package references, served from the team's host in place of the prebuilt build or as static files. `dotnet new fluentcms-plugin` writes a plugin's admin half by default, and it restores from nuget.org now that its packages are published.

**The packages.** Twelve new package ids on nuget.org, each with its symbols: `FluentCMS.Admin.Abstractions`, `FluentCMS.Admin.Components`, `FluentCMS.Admin`, `FluentCMS.Admin.Administration`, `FluentCMS.Admin.RichText`, `FluentCMS.Admin.Hosting`, and the admin halves of the first-party plugins, `FluentCMS.Plugins.Media.Admin`, `FluentCMS.Plugins.Webhooks.Admin`, `FluentCMS.Plugins.Mcp.Admin`, `FluentCMS.Plugins.AiAssist.Admin`, `FluentCMS.Plugins.MultiSite.Admin` and `FluentCMS.Plugins.Search.Admin`. They are a preview. `FluentCMS.Admin.Abstractions` and `FluentCMS.Admin.Components`, the contract of an admin half and the wrapped components it draws with, follow semantic versioning from 1.0.0, as `FluentCMS.Sdk` does, and may break between previews until then; the other ten have no such promise. `FluentCMS.Admin` and `FluentCMS.Admin.Hosting` have the public API analyzer, with every entry unshipped. A half's `AdminRange` is compared with the assembly version of `FluentCMS.Admin.Abstractions`, which is 1.0.0 for every preview of 1.0.0, so build a half again for each preview. `docs/releasing.md` has the policy, under "The admin packages".

**A configured client.** While the admin is on, a `fluentcms-admin` that the options list and that the admin at `/admin` cannot sign in with is named in the startup report, and the host still starts: `admin-client-secret` for a `Secret`, `admin-client-scopes` with those of `profile`, `email` and `management` it lacks (the server holds no client to `openid` and `offline_access`), and `admin-client-redirect-uri` when none of its `RedirectUris` is the callback of the admin the host serves (#3464). The report never holds the secret. A start whose options list no client of the operator's still keeps the clients the host registered before, with their sessions and tokens, and logs which (event id 9003), although the admin adds a client of its own: `ClientRegistration.ContributedByPackage`, a new member that the admin sets on its client, keeps that client out of the rule, and every client listed through the configuration, `cms.Clients`, or the host's `Configure` or `PostConfigure` counts. A `fluentcms-admin` the operator had listed is written as the admin's own client while the section is lost (#3464).

**Browsers.** The admin is built for the last two versions of Chrome, Edge, Firefox and Safari, on desktop and tablet; a phone gets a readable layout that no test covers. Its end-to-end tests run in Chromium against a publish of the reference host on every pull request into `main` that changes more than docs and on every push to `main`, against its image on every push to `main`, and every night in Firefox and WebKit, Safari's engine, against the publish (#3462). Five cases are left out in WebKit, each with an issue: closing a tab with nothing unsaved (#3648), the loading state on the reload of a lazily loaded page, in two cases (#3649), the preview after its page navigates to one without the preview script (#3650), and a link set by keyboard in the rich text editor (#3651).

**Language.** English is the only interface language that ships. Every text is in resource files ready for a translation, which `docs/admin-translating.md` describes. Each user sets the language, when an instance offers more than one, the time zone and the formats of dates, times and numbers on the account page of the admin (#3457).

**Accessibility.** Every view is checked with axe-core against WCAG 2.2 AA, in the light and the dark theme and right to left, with no exception left (#3458). The daily loop runs by keyboard alone, and the criteria of WCAG 2.2 that axe-core does not check have checks of their own (#3460). The admin has not been checked with a screen reader: `docs/admin-accessibility.md` has the script and the table of an optional pass, NVDA with Firefox and VoiceOver with Safari, which no release waits on.

**Known to be missing or open.**

- In WebKit, the preview pane stays ready after its page navigates to one without the preview script (#3650), and a link set with Ctrl+K and an address in the rich text editor is not made and the selected text is lost (#3651).
- An entry action, `[EntryAction]` with `EntryActionBase`, is part of the contract and of a half's manifest, but no view of the admin draws one yet; it is on the follow-up list of the admin (#3610).
- The findings that reviews left for later are on the follow-up lists of #3608 (content), #3609 (identity and access), #3610 (the admin) and #3611 (storage, jobs, events and settings).

## Limits

- **The contract can break between previews.** `FluentCMS.Sdk` and `FluentCMS.Plugins.Abstractions` follow semantic versioning from 1.0.0. Until then a preview may change or remove a public member, and its notes name each such change.
- **A preview makes no promise to upgrade a database.** Each migration stream still has one migration, `Initial`, for each provider, and the changes of the model in this preview went into it. A database made by `1.0.0-preview.1` with the media, search or AI assist plugin is refused with `FCMS1308`, and one without them starts with a warning that names the indexes it lacks (below). A later preview may need a new database.
- **Not verified against a real service.** CI calls no provider. Member sign-in with Apple and AI assist on Azure OpenAI have still not been run against the real service, and are verified before 1.0.0. What the member sign-in run of `1.0.0-preview.1` left open is in #3160.
- **Search on SQL Server matches a part of the text.** The search plugin uses full-text search on PostgreSQL and FTS5 on SQLite. On SQL Server it matches each word as a part of the text, without a full-text catalogue, so it reads every indexed row of the type, locale and state, and `otnet` finds "dotnet" there only (#3049). No provider ranks by relevance or stems the words of a language.
- **AI assist calls OpenAI-compatible endpoints only.** Its providers are `openAi`, `azureOpenAi` and `openAiCompatible`. Ollama is reached through its `/v1` endpoint without a key, and any other client comes through the `IAiClientFactory` slot (#3048). Ollama's `/v1` endpoint reads the older `max_tokens` and not `max_completion_tokens`, which the plugin sends, so an answer is capped at `maxOutputTokens` there only with the site setting `legacyMaxTokens`, which is off by default (#3008). Settings that name `anthropic` or `ollama` are refused with what to use instead, and a configuration section `FluentCms:Ai:Anthropic` or `FluentCms:Ai:Ollama` stops the host.
- **An SSO provider's remote sign-out can come from another site.** `/account/sso/{name}/signout` now ends only the sign-in whose provider `sid` and `iss` the request carries (#3204), but a site that knows them ends that sign-in and its tokens with one top-level link, and a provider that gives one `sid` to every relying party of a sign-in lets each of them do so. Back-Channel Logout is not supported. The other three known bugs in sign-in and sessions of `1.0.0-preview.1` are fixed (below).
- **SQLite with several processes on one file.** A process that waits for a lock can still take it from a holder that is still working, when the holder's lease runs out inside a long write transaction of another connection while other processes keep writing; a holder's own write transactions now renew it (#3186). A `fluentcms schema apply` that notices it lost its lock says so (`FCMS3339` or `FCMS3340`) and is finished by a second run. The other two known bugs in operations of `1.0.0-preview.1` are fixed (#3192, #3212).
- **A storage that instances share is safe only when they share the database too.** An instance that purges, replaces or removes a site deletes the files it wrote even when an asset that another instance imported by a line without a file names them. Import between such instances with `mediaFiles=true` (#3472).

## Changes that break code built before this preview

- **The admin is on by default.** `FluentCms:Admin:Enabled` is true unless it is set to false, in the image and in every host that calls `cms.AddAdmin()` (#3464). An instance that set nothing about the admin now, after the upgrade:
  - serves the admin at `/admin/`, under `FluentCms:ReverseProxy:PathBase` when it is set, with its `config.json` at `/admin/config.json`; the admin's pages carry a `Content-Security-Policy` of their own and `Cross-Origin-Opener-Policy: same-origin`, and no other route changes;
  - registers the public client `fluentcms-admin` of the admin pool at start, a new row of `cms_oidc_application`, with the redirect URI `{public origin}/admin/authentication/login-callback`;
  - counts the admin's files, their compressed copies and fingerprinted paths included, under `FluentCms:RateLimits:StaticFiles:PermitLimit` (15000 a minute per client address), and its page, `config.json` and its calls under the coarse `PreAuth` limit, as `docs/admin-configuration.md` describes under "Rate limits";
  - needs `FluentCms:PublicOrigin` outside Development: a host that started with `FluentCms:Security:AllowRequestOrigin` and no public origin now stops with `FCMS1101`, and so does one whose public origin has a host name that is not ASCII (write it in its `xn--` form) or whose path base holds a character other than letters, digits and `- . _ ~ /`, or a segment of dots only. A command of the host, such as `fluentcms migrate`, needs no public origin, and a start with nothing set stops on the same three refusals as in Production before (`FCMS1102`, `FCMS1105`, `FCMS1106`).
- **To keep what the host had before**, set `FluentCms:Admin:Enabled` to false, `FluentCms__Admin__Enabled=false` for the image: `/admin` answers 404 like any unknown path, no client is registered, and a client the admin registered while it was on is deleted at the next start with its sessions and tokens (#3487). Do so on an instance whose admin is the prebuilt static build or a team's app on another origin, which keeps its own `fluentcms-admin` under `FluentCms:Clients:Applications`; with the admin on, that listed client is the one the admin at `/admin` signs in with too.
- The packed `FluentCMS.Admin.Hosting` depends on `FluentCMS.Core` at its exact version, `[1.0.0-preview.2]` for this preview, since it serves `/admin` with members of Core that no public API file tracks. A host that takes another version of Core with it is told at restore: `NU1608`, a warning only, when it references a newer `FluentCMS.Core` itself, as a host of `dotnet new fluentcms` does, so keep every FluentCMS package of a host at one version; `NU1605`, an error by default, when it references an older one; and `NU1107` when two packages ask for different ones.
- Rotating, revoking or expiring an API key needs every grant of its role as its binding narrows it, as creating it does, besides `apikeys.manage` where the key reaches; without the grants the call is refused with 403. Revoking a key, or expiring it now, revokes the pending invitations it sent (#3262, #3297).
- Revoking an invitation needs every grant of its roles, and so does sending one that ends a pending one to the same address. An invitation is accepted only while its sender still stands: the user is active, the key is neither revoked nor expired, the service account's client still exists, and the sender holds `users.manage` and the roles' grants. Otherwise accepting fails with `FCMS3005`; an invitation sent by the CLI is not checked again (#3297).
- A job that ignores its token past its attempt timeout is abandoned 30 seconds later: the attempt fails with `FCMS2508`, the worker goes on, event 9515 is logged and the counter `fluentcms.job.abandoned` counts it. It may still run beside its retry. `FluentCms:Jobs:MaxAbandonedJobs` (4, a new option) caps how many are left running on an instance, and the gauge `fluentcms.job.abandoned_running` shows them; past the cap such a job keeps its worker until it returns (event 9519), as every such job did before (#3266).
- A rich text URL under `href`, `src`, `url`, `cite`, `action`, `formaction`, `poster`, `background` or `xlink:href` of any node or mark is refused with `FCMS2114` (422) at its path when it has a scheme other than `http`, `https`, `mailto` and `tel`, or is not a string; a URL with no scheme is allowed. The JSON form stored and returned a `javascript:` link as written; only the HTML and Markdown renderers left it out. A URL stored before is left out of every entry read: a `link` mark goes and its text stays, any other key goes alone. A write that carries it on, such as a patch of another field, stores the value without it and logs warning 9405, which names the field and the scheme, never the URL (#3269).
- A secret setting, a key that its settings class marks `[SettingsSecret]` or that is named like a secret, such as `apiKey` of `ai`, is stored in `cms_setting` protected with the Data Protection key ring, as a string that starts with `fcms-protected:v1:`, where it was stored as plain text. A secret stored before is read as it is, and protected by the next write of its settings or by `fluentcms settings reprotect`; while one is left, the startup report lists `settings-secrets-unprotected`, so replace the secrets a backup may have exposed. The secrets are only as safe as the key ring: losing it, or replacing its certificate without keeping the old one, loses every secret setting. A value the ring cannot unprotect reads as its code default, is not inherited by a site from the instance, is left out of `secretsSet` and is logged with event 9804, and the report lists `settings-secrets-unreadable` (#3270).
- Lockout no longer ends the sessions a user or a member already has: the authorize endpoint over a live cookie, the token endpoint and the member pool's cookie check only that the account may sign in, and a new sign-in is still refused while it is locked out. Before, a lockout, which anyone who knows a user name can raise, held a signed-in user at the authorize endpoint and refused its refresh tokens (#3271).
- A configured client with `RequireConsent` whose redirect URIs change at start loses its users' consents and their tokens, so its users consent again (#3272).
- A job of a type the instance has not registered, as in a rolling deploy or after a plugin is removed, is put back for an instance that knows it without using up its attempts (event 9517), and is dead-lettered with `FCMS2501` one hour after it was first put back; each attempt failed with `FCMS2501` before. A recurring job of such a type makes no job on that instance and is logged with event 9518 (#3276).
- Dead-lettered jobs and failed outbox deliveries are removed 30 days after they failed: `FluentCms:Jobs:DeadLetteredRetention` is a new option (30 days), and `FluentCms:Events:Outbox:FailedRetention` defaults to 30 days, where both were kept for good. The outbox removes only a delivery that ran out of its attempts. To keep them all, set either option to an empty value (#3285).
- A user name that is another user's email address, or an address that is another user's name, is refused on any save that sets it, with `FCMS3049` on `userName` or `FCMS3003` on `email`; only a new or changed value is checked. At start, up to 20 such pairs already stored are logged with event 9007, each with the two user ids; rename one of each (#3296).
- An authenticator code is taken once: a code of the time step of the last code accepted, or of an earlier one, is refused at sign-in, on `/account/enable-two-factor` and at `/me/two-factor` (#3296).
- The token endpoint redeems no code or refresh token of a user who must change the password (`invalid_grant`), and `fluentcms user reset-password --password-stdin` sets the forced change, where it cleared it, and says so (#3296).
- The startup refusals `FCMS1102`, `FCMS1105` and `FCMS1106`, the refusals of `fluentcms doctor` and the `public-origin-unset` line of the startup report apply in every environment but Development, where they applied in Production only, so a Staging or custom-named environment needs what Production needs. Without a public origin, the server of the OpenAPI document, and so its OAuth URLs, is the request's path base as a relative URL, where it followed the request's `Host` (#3298).
- `src/FluentCMS.Host/.env.example` has `FLUENTCMS_ALLOW_GENERATED_SIGNING_KEY` and `FLUENTCMS_ALLOW_UNENCRYPTED_KEY_RING` commented out, so a compose stack made from it with no certificates stops with `FCMS1102` and `FCMS1106` until both are uncommented for an evaluation or the certificates are mounted (#3298).
- `PUT /api/management/v1/webhooks/{id}` keeps the stored value of a header sent as `***` only while the URL keeps its scheme, host and port. A `PUT` that changes any of them is refused with `FCMS1560` on `headers.{name}` until it gives the value. It kept the stored value whatever the URL, so a holder of `webhooks.manage` could have the write-only headers sent to a host of their own (#3299).
- `FluentCms:Ai:AzureOpenAi:ApiKey` and `FluentCms:Ai:OpenAiCompatible:ApiKey` are sent only to the new `FluentCms:Ai:AzureOpenAi:Endpoint` and `FluentCms:Ai:OpenAiCompatible:Endpoint`. A host that has either key without its endpoint, or an endpoint that is not an absolute `http` or `https` URL, does not start. `FluentCms:Ai:OpenAi:ApiKey` goes to OpenAI's own endpoint unless `FluentCms:Ai:OpenAi:Endpoint` is set. A site whose settings name another endpoint no longer gets the configuration's key: `openAi` and `azureOpenAi` are refused with `FCMS1685` (409), and `openAiCompatible` is called with no key. Before, those keys went to any allowed endpoint a site named (#3300).
- The MCP tool `unpublish` runs after a dry run, as `{type}_delete` and `bulk` do: a call answers the plan, with the published references that would break, and a `confirmationToken`, and unpublishes nothing; the same call with `dryRun: false` and that token unpublishes. It unpublished at once (#3300).
- `IMcpClients.RemoveUnusedAsync` is a new member with no default, which an implementation other than core's must add (#3301).
- An SSO provider whose authority is a shared Microsoft tenant, `common`, `organizations`, `consumers` or the id of the consumers tenant, on a Microsoft sign-in host stops the host with `FCMS3070`, since the handler cannot check the issuer of such a tenant (#3301).
- The outbox delivers in a lane per owner, each plugin one and core's and the host's handlers together another: an owner's handlers get its events one after another in the order they were recorded, and lanes of different owners run side by side, so a slow handler holds back only its own owner. The order holds on one instance only. The recurring job `events.outbox.drain` is gone, and a start deletes its row: a sweep every minute fails the deliveries whose attempts ran out and kicks a drain when rows are due, so an idle instance adds no job a minute (#3303).
- `activity.retention`, `content.trash.purge`, `oidc.prune`, `members.remove_unverified` and `idempotency.retention` have an attempt timeout of 10 minutes, whatever `FluentCms:Jobs:AttemptTimeout` says, and they and `jobs.retention` are resumable: a run stopped at its limit has succeeded, logged with event 9520, and the next run goes on with what is left, where a backlog longer than an attempt was dead-lettered with `FCMS2508` (#3304).
- Every write of a media asset moves its version on, which `If-Match` checks (below), so the column `version` of `cms_media_asset` went into the media plugin's `Initial`, since a preview upgrades no database. A database made by `1.0.0-preview.1` with the media plugin lacks that column and is refused with `FCMS1308`, at start and by `fluentcms migrate`, with nothing applied; recreate it (#3333).
- A search matches only the searchable fields the caller may read (#3263). The search plugin keeps a row for each searchable field of an entry, so the column `field` of `cms_search_entry` went into the search plugin's `Initial`, since a preview upgrades no database. A database made by `1.0.0-preview.1` lacks that column and is refused with `FCMS1308`, at start and by `fluentcms migrate`, with nothing applied; recreate it and rebuild the index (`POST /api/management/v1/search/rebuild`).
- `ISearchIndex.MatchesByField` is a new member, with a default of `false`, and `SearchRequest.Fields` names the searchable fields the caller may read, or is `null` when it may read them all. An index other than the search plugin's is refused `q` with `FCMS2211` for a caller who may not read every searchable field, until it matches only the fields of `SearchRequest.Fields` and returns `true` (#3263).
- `SystemOperation.Begin` takes the host's `TimeProvider` after the accessor, as `SystemOperation.Begin(accessor, time, Origin.Job, site)`, and stamps the operation with it (#3310). An event read before it is published, with no source set, has the system's source at `DateTimeOffset.MinValue`; the bus stamps it when it is published, as before.
- The clients, `FluentCMS.Client` and `@fluentcms/client`, throw a problem for an empty answer, a 204 or a literal `null` where a call returns a result, which they answered as null or `undefined` before (#3310), and refuse the path segments `.` and `..` (#3273). The calls of `@fluentcms/client` are `async`, so an empty, `.` or `..` segment rejects the promise they return, where it threw before the call returned.
- `POST /me/two-factor/enrol` and `POST /me/two-factor/verify` answer `FCMS3065` (403) to a token whose sign-in on the hosted pages is more than ten minutes old, a refreshed one included, so a client signs the user in again before it sets up two-factor (#3372).
- `PATCH /users/{id}` refuses `mustChangePassword` true for a user without a password (`FCMS3049` on `mustChangePassword`), and such a user who carries the flag is no longer sent to `/account/change-password` (#3378).
- The invitation page refuses a user name that is an email address other than the invitation's own, with one answer whether or not a user has it (#3373).
- A usage row of the AI assist plugin keeps the name its principal had at the call (#3418), so the column `principal_name` of `cms_ai_usage` went into the plugin's `Initial`, since a preview upgrades no database. A database made by `1.0.0-preview.1` lacks that column and is refused with `FCMS1308`, at start and by `fluentcms migrate`, with nothing applied; recreate it, which starts the usage log, and with it the day's budget count, afresh.
- The MCP tool `schedule` with `action: unpublish` runs after a dry run, as `unpublish` does: a call answers the plan with a `confirmationToken` and schedules nothing, and the same call with `dryRun: false` and that token schedules it. A scheduled publish runs at once as before, and refuses `dryRun` and `confirmationToken` (#3361).
- A user keeps at most `maxConsentsPerUser` (20, a new key of the settings area `mcp`, and `McpClientRegistrationPolicy.MaxConsentsPerUser`) MCP clients that the `open` policy approved by consenting. A client counts for a user while the user holds a consent to it, one ended by its session or a password change included until the prune of the authorization server removes it, and for the user who first consented to it for as long as it is there, until that user ends the consent with `DELETE /api/management/v1/mcp/consents/{id}`. A consent that would keep one more ends on the hosted error page with `consent_limit_reached`, whose sentence tells the user to end a consent they no longer use or to ask an administrator, and is logged with event 9008 (#3397, #3441).
- `IMcpClients.RemoveOpenApprovedAsync` is a new member with no default, which an implementation other than core's must add (#3397).
- On SQL Server a start with `MigrateOnStartup` or a `fluentcms migrate` that waits for another process's migrations no longer fails at the command timeout with `Execution Timeout Expired`. It logs event 9305 once after 30 seconds and fails after 15 minutes with a `TimeoutException` that names EF's application lock `__EFMigrationsLock` and says that another process is applying migrations; `migrate` exits with 1 and `FCMS3302`, as on SQLite (#3192).
- On PostgreSQL the same wait, for the advisory lock of the whole run, which had no end and logged nothing, logs event 9305 once after 30 seconds and fails after 15 minutes in the same way, naming the migrations lock of FluentCMS (#3192). A migration that runs longer than 15 minutes now makes the processes that wait for it fail; apply it from one `fluentcms migrate` before the hosts start.
- Event 9305 names the lock in the property `Lock`, which replaces `Written`; on SQLite it holds the row of `__EFMigrationsLock` and its time, and the message reads as before (#3192).
- A change of API keys made by a key, and sending or revoking an invitation by any caller, check the caller again in the transaction of the write: grants cut, or a calling key revoked, expired, rotated without overlap, past the overlap of the secret it presented or no longer allowed from the request's address, after the checks before it, refuse the change with 403 and write and mail nothing (#3481, #3483).
- A host that sets `Events` or `EventsType` on the `OpenIdConnectOptions` of a provider of `FluentCms:Sso` keeps FluentCMS's check of the remote sign-out and of the token's subject and session: FluentCMS's `OnTokenValidated`, `OnRemoteFailure` and `OnRemoteSignOut` run first, then the host's, and an `EventsType` is resolved once a request as the handler would (#3225).
- A write that changes a shared (non-localizable) field, whether a save, a discard of the draft, a version restore or a publish whose hooks change the draft, and a write that adds a locale, advance the draft version of every other locale of the entry too, with a version of its own whose message is `Shared fields changed in {locale}.` or `Added the locale {locale}.`, so a write or publish of another locale with a version read before it answers 412, and of two writes of two locales that cross, one does. An import of an entry the instance has advances the locales the package does not name the same way (#3265).
- A 412 can now come with the caller's own version unchanged: a write that moves the shared fields, or adds a locale, is refused when another locale of the entry moved since the write read it. Read the entry again and retry (#3265).
- The other locales' `updatedAt` and `updatedBy` change with another locale's shared edit or added locale, so a list sorted by `updatedAt` moves them, and an import's check that a locale is the same moment as the package's sees them as changed (#3265).
- The versions a locale takes for another locale's shared edit count against `MaxVersions` and can prune that locale's own older versions. No event or webhook announces them, so a version or ETag kept from an event goes stale (#3265).
- A list with `locale=all` holds every entry the caller may read once, also one with no row in the site's default locale, and is filtered, sorted, paged and counted by the entry's row in the first locale, the default and then the site's order, that has one the caller may read; it was the default locale's rows alone. A filter or sort on a field the caller may not read in one of the locales it reads is refused, the message naming that locale. A search with `locale=all` searches the first locale the caller may read, and lists an entry only by its row there, under that locale's row rule (#3277).

    ```sql
    SELECT format('ALTER TABLE %I ALTER COLUMN %I TYPE %s COLLATE "C";', c.table_name, c.column_name,
               CASE WHEN c.data_type = 'character varying' THEN format('character varying(%s)', c.character_maximum_length) ELSE c.data_type END)
    FROM information_schema.columns c
    WHERE c.table_schema = current_schema()
      AND c.data_type IN ('text', 'character varying')
      AND c.column_name <> 'locale'
      AND c.collation_name IS DISTINCT FROM 'C'
      AND EXISTS (SELECT 1 FROM information_schema.columns d WHERE d.table_schema = c.table_schema AND d.table_name = c.table_name AND d.column_name = 'document_id' AND d.data_type = 'uuid')
      AND EXISTS (SELECT 1 FROM information_schema.columns s WHERE s.table_schema = c.table_schema AND s.table_name = c.table_name AND s.column_name = 'state' AND s.data_type = 'smallint')
    ORDER BY c.table_name, c.ordinal_position;
    ```

- `fluentcms schema apply` lists under `Left alone:` a content text column whose collation is not the model's, `C` on PostgreSQL and `Latin1_General_100_BIN2` on SQL Server, and `--script` writes the line as a comment: `column title on table cms_article, whose collation is the database's default and not C as in the content model; schema apply does not change a collation, so a sort and a cursor on the column follow the one it has until it is altered by hand`. Such a column is one of a table made before #3308 on PostgreSQL or before #2874 on SQL Server, or one altered by hand. Schema apply does not change it, with `--allow-destructive` neither, since the change rebuilds the column's indexes and locks the table, SQL Server refuses it on an indexed column, and it moves what every sort and cursor on the column returns. On PostgreSQL alter the columns with the statements that the query in the notes of #3308 writes. On SQL Server drop the indexes, statistics and check constraints that read the column, alter it with its own type and nullability, as `ALTER TABLE cms_article ALTER COLUMN title nvarchar(max) COLLATE Latin1_General_100_BIN2 NULL`, and run `fluentcms schema apply`, which makes the model's indexes again; content text has no check constraint in the model, so make again any that was made by hand. A PostgreSQL database whose own collation is `C` lists its columns too, until they are altered to `COLLATE "C"`. That alter rebuilds every index on the column and holds an `ACCESS EXCLUSIVE` lock on the table until it is done, although the order stays the same, so do it in a maintenance window, or leave the line as it is. SQLite's model gives no collation, so nothing is listed there. A run that leaves something alone, a column or a plugin's table, and has nothing else to do now ends `Nothing to apply; what is listed above was left alone, and the schema history records schema {hash}.` in place of saying that the content tables match the schema; it still exits with 0 (#3476).
- The specification states the order of text on each provider. SQLite and PostgreSQL sort content text by code point. SQL Server sorts it by UTF-16 unit, which differs only around U+FFFF: a character at U+10000 or above, such as an emoji, comes before one in U+E000 to U+FFFF there, such as `Ａ` (U+FF21) or U+FFFD, and after it on SQLite and PostgreSQL. A cursor continues each provider's own order correctly. A client that sorts or compares pages itself compares by UTF-16 unit for SQL Server, as JavaScript's `<` does, and by code point for SQLite and PostgreSQL. Content moved to another provider can list such texts in another order (#3476).
- Every answer of `/api/management/v1/api-keys` that carries a key, the list, `GET /api-keys/{id}`, the create, the rotation, the expiry and the change of addresses, has `maxOverlapSeconds`: the longest overlap a rotation takes, in whole seconds as a JSON integer, which is `FluentCms:ApiKeys:RotationOverlap` rounded down to whole seconds and what a rotation that leaves `overlapSeconds` out gets. A longer one is still refused with `FCMS3026`. A client offers the range before it rotates instead of learning it from the refusal (#3497).

Each area of `GET /api/management/v1/settings` says it as `instanceOnly`, for a plugin's area as for core's, so that a client sends such an area to `/settings/{area}/defaults` without knowing it by name. The flag only describes the area in that list and changes nothing about how the area is read or written. A site write to such an area through `PUT /settings/{area}` is still accepted and stored, and has no effect only because the area's code reads the defaults; `ISettings<T>.GetAsync(site)` still gives the site's values, so the flag is true only when the area's own code reads with `GetDefaultAsync` (#3499).
- A callback registered on the `Lost` token of a lock that throws is logged as a warning with event 9167 (`LockLostCallbackFailed`) and what it threw, once, on every provider; the other callbacks run and the lock is lost all the same. Before, the lock's renewal loop logged it as a renewal that failed (9162) and logged the loss (9161) a second time (#3522).
- A request whose key passed its window and was removed after its lease ran out puts its claim back at its next renewal and goes on holding the key, logged with the new event 9146, so its response is kept for a repeat; if another request claimed the key first, the request is cancelled as after a takeover (#3523).
- Writes, publishes, unpublishes, schedules, scheduled jobs, imports, trash, restore and purge of one entry take its rows in one order, its `cms_document` rows first, each by its primary key and ordinal by locale code, so two of them that cross wait for each other. On PostgreSQL and SQL Server a publish of one locale and a shared write through another, a scheduled job and a write that ends its schedule, or an import and a shared write could deadlock, and one of them ran again after about one second on PostgreSQL and five on SQL Server (#3524).
- A save and a version restore decide their own status from what is stored once their swap holds the row, so a publish or an unpublish of that locale, or another locale's publish of the shared row, that committed between the write's read and its swap no longer leaves a stale status, such as `Modified` for a draft equal to what is published, `Draft` for a locale published or published and unpublished meanwhile, or `Modified` for one unpublished meanwhile (#3524).
- An unpublish decides whether it removes the shared published row under the holds of every locale row, so a publish or an unpublish of another locale that commits meanwhile no longer leaves a published locale without its shared row, or a shared row that no published locale uses (#3524).
- A trash, a restore or a purge of an entry to which a locale was added meanwhile runs again with that locale, so its hooks, checks and `EntryTrashedEvent` cover it (#3524).
- A release of the migrations lock that fails is logged as a warning with event 9307 and no longer replaces the outcome of the migration. The providers of SQL Server and PostgreSQL release every share, with a timeout of 5 seconds, or close the connection, so that no lock stays in the pool after a failed or cancelled migration (#3528).
- A database that another process is creating is no longer refused with `FCMS1308` as one of an earlier baseline, by a start, `migrate` or `doctor` (#3528).
- `docs/content-migrations.md` gives the query that finds the session holding the lock on each server, and lists the waits that the command timeout still ends (#3528).
- `JobsBuilder.AddJob<TJob, TPayload>(type, attemptTimeout, resumable)` is public, so a host registers a resumable job with `cms.Jobs.AddJob<TJob, TPayload>(type, attemptTimeout, resumable: true)`, as a plugin does through `IPluginServiceBuilder`. Such a job stops on its token wherever it is with what it did kept, and something runs it again, such as a schedule, since a run stopped at its limit has succeeded and is not retried (#3529).
- The schema readers of PostgreSQL and SQLite list an index whose keys are expressions by its name, as the check behind `FCMS1308` and event 9306 finds the indexes of a model. On PostgreSQL an index of expressions alone, such as a GIN index on `to_tsvector`, was not listed, so a plugin whose model has one would be warned of it at every start, or refused for a unique one; on SQLite such a key failed the read. A key that is an expression is listed with an empty name. SQL Server indexes no expression, and an index on a computed column or with a filter was already listed (#3530).
- `fluentcms schema apply` and the schema sync of a development host leave alone an index on a content table that has an expression key and that the content model lacks, such as one made by hand on `lower(title)`, since the content model cannot declare one: apply does not drop it, and the sync does not report it with event 9303. On PostgreSQL an index of expressions alone was kept so before, since it was not listed, while one of columns and expressions was listed by its columns alone and dropped; on SQLite the read failed. An index of plain columns that the model lacks is dropped or reported as before (#3530).
- A sign-out whose `user.sessions_ended` or `member.sessions_ended` row cannot be written still finishes: the logout endpoint, the member logout page and a provider's remote sign-out delete the cookie and answer as they do otherwise, where they answered 500 and left the cookie in the browser with its tokens revoked. A sign-in over another one, or with the second factor, likewise goes on. That holds for any failure of the write, whatever the provider throws for it, SqlClient's bare `InvalidOperationException` for an exhausted pool included, except `OutOfMemoryException` and the refusal of a write inside a transaction someone else began (`FCMS3009`, `FCMS2602`), which fail the request as before. The failure is logged as an error with event 9012 (`SessionEndNotRecorded`), with the pool, the id, the reason, the type of the failure and, for an error of the database, its `SqlState` and error code, without its message or stack, and no row is written, so that line is the only trace of the end and an operator who audits sign-outs alerts on it (#3531).
- `member.sessions_ended` with the reasons `password_changed`, `deactivated`, `login_removed` and `deleted` is written only when the member had a live session, a valid authorization or a valid token that has not expired. Every authorization and token of the member is revoked as before (#3531).
- A publish scheduled, or due, while a locale is added to the entry publishes at its time. Adding a locale moves the version of the entry's other locales, and such a schedule was skipped with `FCMS2409` ("the draft changed") although its draft had not changed: a schedule saved meanwhile kept the version it had read, and a job compared the schedule it had read before its transaction (#3534).
- A claim of the outbox drain that fails or is stopped after its update, before its rows are read back, gives them back with the attempt it counted. They stayed leased with one attempt more, and the sweep failed those on their last attempt though no handler saw them (#3537).
- No outbox handler starts once its lane is told that the host is stopping, also when the stop comes during a renewal of the lease or just before the hand-off. Such a handler could start after the drain returned, while its row was given back (#3537).
- A stopping host's job runner returns within `JobRunnerOptions.ReleaseTimeout` (5 seconds) after the grace period, also when a cancelled job writes its release inside the cancellation, as on SQLite while the command waits for the lock. Such a release held the stop for up to the command timeout of each such job before the time of the releases even began. Each worker's job is told of the stop in a thread-pool work item of its own, so a release written so, or a cancellation callback that blocks, no longer delays telling the others, the outbox drain included. A job whose release is not written by then keeps its lease, is taken over once the lease ends and is never marked done, and event 9514 is logged (#3538).
- The bound has a cost: a release that needs longer than `ReleaseTimeout` but would have succeeded used to finish before the stop returned. Now the stop returns and logs 9514, and unless the release still lands before the process ends, the job waits for its lease to end with its attempt spent (#3538).
- What a callback of the stop's cancellations throws while the stop waits is thrown from `StopAsync`, as before; what one throws after the stop has given up waiting is logged as a warning with event 9522 (`StopCallbackFailed`) (#3538).
- A content hook that had not ended when its caller was cancelled, such as by a client that went away or a lost `Idempotency-Key`, is logged as a warning with the new event 9408, naming the hook, its kind and its type; only a hook that timed out was logged, with event 9406 (#3542).
- On SQL Server without MARS, a write whose hook was left inside a command, its reader open, fails with what it failed with, its cancellation or `FCMS2410`, instead of SqlClient's refusal of the rollback beside that reader, which is logged with the new event 9409. Its transaction and its locks then stay until the scope is disposed, which rolls them back; nothing of it commits (#3542).
- Disposing a handle of the database lock waits at most 5 seconds, as the job runner's disposal does, for the callbacks registered on its `Lost` token once the loss is being told. A callback that does not return kept the disposal waiting for it. When the bound is reached the disposal returns, after the release, and logs a warning with event 9168 (`LockLostCallbackSlow`); the callback runs on, the token stays usable until it returns, and what it throws then is logged with event 9167 as before (#3544).
- A stopping host settles the outbox rows already delivered and gives back the rest also when the stop comes during the read of the site's default locale for a delivery, which the drain no longer waits for, or during the disposal of a delivery's scope, which goes on without it. A read or a disposal longer than half of `JobRunnerOptions.ReleaseTimeout` left the delivered rows leased, and one longer than all of it the rest too (#3548).
- The rows of a batch that the outbox drain gives back, those that wait `MissingHandlerDelay` and those that go back at once, go with one write at the end of the batch, which has what is left of the stop's `ReleaseTimeout`. Each kind had a write of its own, so a slow first one could leave the next none. The lease of the rows given back so far is renewed with the rest of the batch (#3548).
- A drain job that comes while the lanes of a cancelled drain of its instance still run, as when a drain job that lost its lease returned at the end of `ReleaseTimeout` with a release in flight, only signals and ends, as one that finds a drain running does, so that it cannot deliver an owner's later rows before the earlier ones go back. The instance drains again only once those lanes have ended, and then at the next kick or sweep, since nothing kicks a drain when they end. A drain that returns so is logged as a warning with event 9628 (`DrainLeftLanes`) (#3548).
- Event 9603 says that a write given up may still land, and that a row on its last attempt is left as failed rather than delivered again: `Could not write the outcome of outbox delivery {Id}, or gave the write up, which may still land; if it does not, the delivery keeps its lease and is tried again when the lease ends, or left as failed if that was its last attempt.` (#3548).
- The lock timeout of a write is set for its transaction alone: `SET LOCAL lock_timeout` on PostgreSQL, `SET LOCK_TIMEOUT` on SQL Server, set back before the transaction ends so that no connection keeps it, and the busy wait of the transaction's `BEGIN IMMEDIATE` on SQLite. A write sends one statement more on PostgreSQL and two more on SQL Server (#3573).
- `PluginDbContext<TPlugin>.HoldSiteAsync(SiteId site, CancellationToken cancellationToken = default)` holds the row of a site shared to the end of the context's current transaction, for a plugin's own writes of a site's rows, and is refused with `FCMS2301` when the site is gone. Without an open transaction of the context it throws `InvalidOperationException`; it begins none of its own. A plain save holds nothing, as before. Hold several sites in ascending order of `SiteId.Value`, and never in a content hook, where on SQL Server a deletion of the same site queued meanwhile and the hold wait for each other until a timeout fails the content write (#3586).

## Fixes

- On SQLite a host that holds a database lock renews it inside each of its own write transactions as it commits, once half the lease has passed, so a process that waits for the lock no longer takes it from a holder whose lease ran out inside its own long write transaction, such as a `schema apply`, a schema sync or an import, while other processes keep writing. This was a known bug of `1.0.0-preview.1`; what is left of it is under "Limits" (#3186).
- Any change that gives an admin user a new security stamp revokes every session of the user with its tokens, in the same save, so an access token issued before it is refused at its next request: a password change or reset, a new name or address, deactivation, a removed external login, and two-factor turned on or off. A third-party client's consent ends too, so the client asks again. Before, those access tokens worked until they expired, a known bug of `1.0.0-preview.1` (#3202).
- In both pools the authorize endpoint keeps the cookie of the hosted pages when it asks for a new sign-in, for `prompt=login`, a `max_age` the sign-in is older than, a sign-in past `AbsoluteSessionLifetime` and a second factor the role now requires, and sends the user to the login page over it. The request comes back with a protected `fcms_reauth` mark, bound to its `client_id` and `code_challenge` and good for 15 minutes, which only a newer sign-in answers. So another site can no longer end a sign-in with one link, a known bug of `1.0.0-preview.1`. A cookie past `AbsoluteSessionLifetime` no longer opens the hosted pages that need a signed-in user, and the user signs in again over it (#3203).
- The remote sign-out path of an SSO provider, `/account/sso/{name}/signout`, ends a sign-in only when the request carries `sid` and `iss`, each once, equal to those of the id token the sign-in was made with through that provider, and then ends the server session's authorizations and their tokens with the cookie. A provider whose id token carries no `sid` can therefore no longer end a sign-in this way. Anything else ends nothing and gets the same empty 200, with `Cache-Control: no-cache, no-store`. A sign-out logs event 9046 and an ignored request 9047. Before, any request ended the cookie of any user who had signed in through that provider, a known bug of `1.0.0-preview.1`; what is left of it is under "Limits" (#3204).
- When `AbsoluteSessionLifetime` is set, the tokens of a code flow end that long after the sign-in on the hosted pages they came from, in both pools. They counted from the authorize request, so they could live up to twice the lifetime after the sign-in, a known bug of `1.0.0-preview.1`. A member's direct login still counts from its grant (#3205).
- On Windows the signing and key-ring certificates loaded from PFX files load with `EphemeralKeySet`, so no private key file is left in `%APPDATA%\Microsoft\Crypto\Keys` when the process is killed, a known bug of `1.0.0-preview.1` (#3212).
- A sign-in with the second factor revokes the tokens its server session was issued without it, those of a client with `RequireConsent` included, and keeps the consent; the user's other sessions stay. Before, those access tokens lived until they expired (#3228).
- The daily purge of deleted media assets, its cleanup of their variants and the deletion of a site delete an asset's file only when the asset owns it and no other asset of the library names it. They deleted the file whatever owned it, so purging one of two assets on one key took the file the other still served (#3264).
- The attempts to one webhook wait in its queue, as rows of `GET /webhooks/{id}/deliveries` with the new `state` `queued`, and go one after another in the order of their events, each as soon as the one before ends, holding no worker. While an attempt was in flight, every other attempt rescheduled itself for that attempt's timeout plus a random delay, so a burst went at about one attempt a timeout and out of order. The new recurring job `webhooks.queue`, every minute, wakes a queue whose head and last claim are at least 10 minutes old with nothing in flight, and logs warning 9252 (#3268).
- The HTTPS redirect skips `/health`, and the `--probe` of the reference host follows no redirect and reads `urls`, `http_ports` and the path base from the configuration files too (#3275).
- The URLs of a media asset that a Delivery read or a media reference answers, its original, its preset URLs and its template, and those of `IMediaService.GetImageUrlAsync` carry `v` from the asset's checksum, as the Management API's do, so a replace gives them new URLs. They had none, so a browser or a CDN kept serving the old file under the same URL for up to the media `CacheControl`, `public, max-age=86400` by default (#3278).
- `/media/{id}/original/{fileName}` answers `HEAD` and a `Range` on the local disk, S3 and Azure Blob: 206 with `Content-Range` for a range and 416 past the end, so a player seeks and a download resumes. It sent the whole file to every request (#3279).
- A webhook receiver's answer excerpt or an error text is stored without control characters other than tab and line breaks, and never cut inside a surrogate pair, so a 2xx whose answer held a NUL is recorded once; on PostgreSQL the write failed after the 2xx and the attempt was sent again (#3299).
- A write's events are delivered at once while a failed drain job of the outbox waits for its retry, which the kick took for a drain already queued (#3303).
- The multi-site plugin removes a deleted site's host names in the outbox handler `multi-site.cleanup.site.deleted`, so a removal that fails or is cut off is tried again. It ran once in process and was cut off after `FluentCms:Events:Handlers:Timeout` (5 seconds), which could leave the gone site's rows of `cms_multi_site_host` for good (#3329).
- Writes of one media asset at once without `If-Match` are each applied to the asset as the other left it, so saves of its alt text in two locales keep both; a write that loses five times running is refused with `FCMS3105` (412) (#3343).
- Wrong current passwords or codes a session sends at once are checked no more than the lockout's limit, however many they are. They all read the user before any of them saved, so only one was counted, and a right password among them was checked without being counted and answered either way: a concurrency failure when its save lost, which told the sender it was right. A guess now takes its place in its count, in a save that goes through and is made again on what is stored when it loses, before it is checked. One that finds the sessions kept out is refused unchecked, and one whose tries at a place run out, twice the lockout's limit, ends with the concurrency failure, unchecked too. A wrong one keeps its place and counts towards the lockout; a right password takes the new one in a save that gives its place back, made again when it loses, and is answered as a wrong one if its tries run out; a right code is taken in the save of its step, and one that loses it is refused like a wrong one, since a code is taken once (#3447).
- A call of `CmsUserManager` whose save fails puts back the flag of the forced password change, or the deactivation, only when that save did not reload the user with what is stored, which another request may have changed. Put back over a reload, the stale value would have been stored by a later save in the same scope, which could have reactivated a user another request deactivated; no caller of core saves again after such a failure, so this was latent (#3447).
- `docs/host-configuration.md` no longer says that the token endpoint refuses a code or refresh token of a user who is locked out, which #3271 ended (#3447).
- The `Pack` job of the `Publish` workflow fails, a dry run too, when a package it would push depends on a FluentCMS package that it would not, and names both; `eng/check-dependencies.cs` makes the check (#3453). This preview pushes every package, the admin's included (#3464).
- An SVG uploaded with `Svg` set to `sanitize` could run script in a page that inlines it: a CDATA section in a text element, under a root with a namespace prefix such as `<s:svg>`, was stored as it was, and a page that parses the file as HTML reads such a section as a comment that ends at its first `>`, so what follows became markup of the page, an `<img onerror=…>` for one. A sanitised SVG is now written with SVG as the default namespace and no prefix on any element, with no XML declaration, CDATA section, comment or processing instruction, and with text and values escaped, so that an HTML parser reads it as an XML parser does. The hole existed before this preview. SVGs already stored are not changed, as the item on sanitising SVGs above says (#3484).
- A sanitised SVG is written with `\n` for a new line on every platform, so that sanitising it again on another one gives the same bytes and an import line can take its key (#3484).
- A request with an `Idempotency-Key` whose work answered before its client went away keeps that answer although the client went away while it was being written, so a retry with the key is answered it, with `Idempotent-Replayed: true`, and runs nothing. The key was held without an answer until its lease ran out, and a retry then ran the request again. A client that goes away while the work still runs leaves the key held without an answer, as before, so a bulk cut short, which answers 200 with its remaining items not run, keeps nothing, and a retry after the lease runs it again. That window stays open: a create whose commit is done but whose client went away before the service returned, as while the entry is read back, where a client's timeout most often lands, and a bulk whose first items committed, still run again on a retry after the lease. Writing an answer after the client left takes `InProgressTimeout` at most; one that takes longer is not kept, logged with the new event 9147, and the key can then be held for up to twice `InProgressTimeout` (#3485).
- A host's own events on a Google, Microsoft, GitHub or Apple provider of `FluentCms:Members:Providers` (`member-{name}`), set as `Events`, as `EventsType` or as a delegate of `OnRemoteFailure` or `OnTicketReceived`, in a `Configure` or a `PostConfigure`, keep FluentCMS's part of those two events: an error at the provider goes back to the member login page with a `member.login_failed` row, and the sign-in names the provider, so the external login page accepts it. FluentCMS's part runs first, then the host's. Before, a host's events could replace that part: an `EventsType` wherever it was set, `Events` or either delegate set in a `Configure` registered after `AddFluentCms` or in a `PostConfigure`, and `Events` whose methods did not call their delegates. Only the event that lost FluentCMS's part changed: without `TicketReceived`, the external login page refused the provider's sign-ins; without `RemoteFailure`, an error at the provider went to the error page with no row (#3564).
- A read that falls back, a list with or without `q` or an entry read by id that has a row in the requested locale, answers when a field limit of the caller's grant in a fallback locale leaves out some of the fields the entry lacks: that locale fills only the fields the caller may read in it, and a field it may not read there falls back further along the chain or stays empty. It refused the whole read with 400 `FCMS2202` on `fields`, also when the caller's own `fields` selection was valid in the requested locale; such a selection now answers. A `fields` selection that names a field the caller may not read in the requested locale is still refused with `FCMS2202` (#3566).
- Wrong current passwords a member's token sends at once to `POST /api/members/v1/me/change-password` are each counted towards the lockout, and no more of them are checked than its limit, however many they are. They all read the member before any of them saved, so only one was counted, and a right one among them was answered with `FCMS3174` (`MemberChanged`) when its save lost, which no wrong one gets. A current password is now counted, in a save that is made again on what is stored when it loses, before it is checked; one that finds the member locked out is refused unchecked with `FCMS3167`, as before, and one whose count keeps losing gets `FCMS3174` unchecked, whether it was right or wrong. A right one gives its count back in the save of the new password, lifts the lockout its own count set, is made again when that save loses, and is answered as a wrong one if its tries, twice the lockout's limit, run out (#3597).
- Wrong passwords the member login page and the direct login grant check at once are each counted towards the lockout. Each count that lost its save to another was dropped; it is now made again on what is stored, unless the member is locked out by then (#3597).
- `fluentcms user create --password-stdin` and `user reset-password --password-stdin` no longer keep a byte order mark as part of the password. PowerShell on Windows can write one before what it pipes, and the user could then not sign in with the password that was piped. A user made that way gets a working password with `user reset-password --password-stdin` (#3621).
- The save of new recovery codes, by `POST /me/two-factor/recovery-codes` and by turning two-factor on through `POST /me/two-factor/verify` or `/account/enable-two-factor`, is made again on what is stored when it loses to another save of the user, as the other saves of `CmsUserManager` are, without checking the code again, and the codes answered are those stored. It was made once, so a right code, already taken, was answered with a 500 when that save lost. A save whose tries run out is refused with `FCMS3049`, and so is one for a user another request deactivated meanwhile; one for a user whose two-factor another request turned off is refused with `FCMS3061`; none of them stores codes (#3666).
